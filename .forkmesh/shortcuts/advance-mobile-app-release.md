# name: Advance the mobile app toward App Store release
# description: Check mobile development progress, run quality checks and a release build, fix the clearest blocker, and report the remaining path to submission.

Advance the ForkMesh mobile app toward a verified App Store submission. Work from repository evidence and leave the project in a better, reviewable state by the end of this run.

1. Establish the current state before editing. Inspect `git status`, recent changes under `native/ios/` and `native/android/`, relevant open issues and pull requests, `native/ios/Config/Version.xcconfig`, `native/android/app/build.gradle.kts`, `codemagic.yaml`, `docs/native/IOS_RELEASE.md` and `docs/native/ANDROID.md`. Distinguish completed work from open, blocked, or unverified work.
2. Run the native quality gates: `.forkmesh/shortcuts/test-native-ios.sh` (ForkMeshCore tests, SwiftUI parse, project generation) and, from `native/android/`, `./gradlew :core:coreTest :app:assembleDebug`. Record the exact commands and results. Diagnose failures from their output rather than bypassing checks.
3. Execute at least one real release build command on every run. The iOS app only compiles on macOS: that is Codemagic's `ios-native-build`, so on Linux build the Android release APK (`./gradlew :app:assembleRelease` from `native/android/`, with `tools/android-toolchain.sh` and `tools/loopback-netns.sh` when needed). A missing SDK, signing identity, network permission, or platform is a reported blocker, not a successful build and not a reason to claim an artifact exists.
4. Select the highest-priority, well-supported blocker that can be safely addressed in this repository. Prefer release correctness, store compliance, authentication and account deletion, privacy disclosures, production connectivity, signing/build configuration, launch stability, and failing tests over cosmetic cleanup. Make a focused change, add or update tests, and rerun the affected checks and release build. Do not churn version numbers or store metadata without a concrete release reason.
5. Keep changes isolated and reviewable. Preserve unrelated work, inspect the final diff, and use the available git and issue tools to leave a concise commit on the branch when code changes are warranted. Never open a pull request and never merge your own work.
6. Do not upload binaries, submit a store release, accept legal agreements, purchase services, or reveal or modify signing credentials without explicit human approval. Prepare everything possible up to that boundary and identify the exact person, credential, console action, or macOS runner needed to cross it.

Finish with a short daily release report containing: progress since the previous repository state, checks and build commands with pass/fail status, artifact path and type if produced, the blocker addressed, remaining App Store checklist gaps, and the single best next action.
