The mirror becomes a front door

ForkMesh's current main branch gives an independent mirror more ways to be a useful repository entrance, then carries that shorter path into mobile agent work, installable tools, and the tasks developers move every day.

August 31, 2026Product update7 min read

The mesh keeps moving ended with more candid recovery and a phone that could participate in the foreground. This update follows the next step: a healthy independent node can do more than wait behind a routing layer, and the everyday work around that node is becoming easier to carry between web, desktop, and mobile.

This update covers the 322 commits that landed on main from August 28 through August 30. The repository's complete latest manifest still points to v0.7.29. A detached-signature Linux candidate exists for v0.7.95, while later tags do not establish a complete cross-platform release. Unless a section says otherwise, the work below is merged on current main, not promised in every installed client or hosted surface.

A mirror can be a destination

ForkMesh's direct-HTTPS path now gives a public mirror a standard Smart HTTP URL of its own. A Git client can follow a temporary redirect to a fresh, proven mirror instead of sending repository bytes through the control-plane Worker. The stable ForkMesh clone URL remains the starting point, so routing can change without changing repository identity.

The same node can serve the repository dashboard from the site's own build assets stored in the mirrored repository. Code, branches, commits, diffs, releases, and Git-backed issues, pulls, and discussions resolve from that mirror's validated local state. Repository pages can also list independently reachable mirror pages, giving a developer an explicit route when the canonical App origin is unavailable.

Synchronization is less dependent on a tight polling loop, too. Managed peers announce repository and replica changes over the node event socket, then fetch the actual Git or projection bytes over HTTPS. Events are coalesced, while a bounded reconciliation interval remains as recovery for a missed or disconnected stream. Large repository payloads never move inside the event socket.

The shorter route keeps a narrow authority

Serving a page from a mirror does not make that mirror another account database. The mirror's local public projection is an allowlist, not a copy of D1: passwords, controller sessions, encrypted account rows, private inboxes, direct messages, notes, payments, and administration state do not enter it. A last-good projection can keep public status and network views useful during an outage, with response headers identifying that source.

For a signed-in repository link, the controller can issue an expiry-bounded portable grant containing opaque account and session identifiers plus a public username. The handoff uses a form body and an HttpOnly cookie rather than putting the grant into a URL, referrer, or local storage. The mirror verifies the controller signature; it never receives a password or bearer credential. This is login continuity for a bounded repository experience, not independent account recovery or a new payment authority.

Public upload-pack reads may use the direct route without a routing capability. Control, mutation, private, and non-Git repository requests keep their capability checks, and unknown, private, disabled, or integrity-quarantined repositories retain uniform failure behavior. Direct HTTPS is replaceable transport metadata; signed repository identity and the integrity checks remain separate.

A small coding agent fits on the phone

The Flutter client now contains a focused coding-agent loop for a local repository. A developer can connect an Anthropic or OpenAI API key, ask for a change, watch tool calls and results, steer the run, and turn a completed branch into a pull-request proposal. Provider credentials use the mobile secure store and the implementation sends each key only to its selected provider.

The tool set is deliberately smaller than desktop Codex or Claude Code. It can list, search, read, write, and replace repository files, inspect Git status, and commit. It has no shell, cannot execute project code, and does not claim to run tests or linters on iOS. Read-only mode refuses mutating tools rather than pretending they succeeded.

Each run starts only from a clean working tree, creates an isolated branch, and restores the base branch after finishing. The phone runs one session per repository at a time because its Dart Git engine does not provide linked worktrees. Interrupted runs leave durable branch records for cleanup; publishing still requires the explicit push-and-open step. This is substantial current-main implementation with an end-to-end repository test, but the App Store checklist remains unfinished, so it is not evidence of a public mobile release.

A broader mobile design pass landed beside it: one type scale, consistent fields and controls, reduced-motion-aware haptics, skeleton loading states, gentler state transitions, and regenerated platform icons from the official mark. Those changes are merged and tested, but still share the same store-release boundary.

The Market is becoming a real boundary

The Marketplace now has a more general contract for software that plugs into ForkMesh. Package manifests declare host-neutral contribution sockets instead of requiring the core app to branch on every package ID. The web host currently understands dashboard-page and Worker-HTTP sockets; package code is staged into generated build directories during deployment rather than copied into tracked application source.

Installation and removal carry a paired lifecycle. A package validates its manifest, permissions, paths, signature, and content before activation. Package-owned database migrations need both up and down steps. Uninstall quarantines the package, stops active work, detaches its UI and capabilities, clears package-owned settings and cache, and rolls back if removal cannot complete. A licence, creator attribution, user output, and purchase receipts remain distinct from whether the package is currently installed.

That boundary is now doing visible work. CRM contributes a dashboard and Worker module; Sentry owns its connection and cached issue data inside a removable desktop package; and Tasks, Calendar, and Notes are catalog-discovered productivity pages instead of hard-coded core routes. The public Market adds repository links and ratings, while the desktop can separate installed packages from those still available. Catalog publication alone does not grant runtime permission, and bundled discovery is not the same as activating an external package.

Daily work takes fewer detours

Organization tasks on the web grew from a catalog view into a working surface. Developers can create and edit tasks, inspect status and priority, manage assignments, add follow-ups and images within bounded limits, request QA, reply, complete or reopen work, and copy a task as an agent-ready prompt. Task edits now refresh immediately in the desktop, and issue descriptions show their dependency relationships instead of hiding that context behind another view.

Team chat can mention @all, shows teammate roles in its roster, and links briefing messages back to tracked work. Agent runs can stay on the current page instead of pulling the operator away from the surface that launched them. Prompt editors gained local spellcheck squiggles, while finished sessions can be selected and removed together.

Several changes make those richer surfaces feel lighter. The desktop paints its shell before deferred pages are built, repository tabs remain lazy until opened, pull refresh moves off the UI thread, and large diff HTML is appended in batched layout updates. Web issue submission avoids a cold tracker scan and returns its accepted result sooner. These are responsiveness and workflow changes backed by focused budgets and regression tests, not a performance benchmark for every repository or machine.

Release evidence still sets the boundary

The window includes annotated tags through v0.7.99 and repeated work on native packaging, direct-mirror integration, and release provenance. It also contains a detached-signature v0.7.95 candidate manifest with Linux x86_64 artifacts. That candidate is intentionally isolated from latest: the release workflow promotes only after the complete Windows, macOS, and Linux installer matrix shares the required provenance.

As of this repository snapshot, the signed complete latest channel remains v0.7.29. The direct-mirror, mobile-agent, Market, task, accounting, and desktop refinements described here therefore need their matching hosted rollout or a later complete signed release before they should be described as universal availability. Annotated version tags alone do not cross that line.

The next useful proof is operational: validate direct repository pages and portable handoff across independent nodes, complete the native release matrix, and run the mobile checklist on real devices. Until then, the accurate story is still a strong one: current main moves more work onto routes and surfaces developers can inspect, without pretending every route is already in every hand.
