Introducing ForkMesh: code beyond a single host

The ForkMesh team June 23, 2026 6 min read

Most code today lives on a hosted service, under that service's terms. ForkMesh offers another option: a distributed Git network where your code stays on your machine, every action is signed with your key, and eligible mirror operators may receive transparent community incentives. Selection and payment are never guaranteed.

Today we're opening up ForkMesh — an open-source desktop node and relay for hosting, mirroring, discovering, and discussing software projects without depending on a single code-hosting company. It is not a front end for an existing forge and it is not a blockchain repo. It's a different shape: a mesh of peers where the network coordinates, but no one in the middle holds the only copy of your code.

Why we built it

Centralized forges have been great for collaboration, but they concentrate risk. Accounts can be suspended, services change direction, and a project that lives in exactly one place depends on whoever controls that place.

ForkMesh starts from a simple premise: the canonical copy of your code is the bare Git mirror on your own disk. The network's job is to help people find it, clone it, talk about it, and mirror it — not to be the single place everything depends on.

What's different

Six ideas shape how ForkMesh works.

🗄️

Your machine is the server

The relay is a control plane, not storage. Git objects stream from a connected host node — there is no central repository store.

🔑

Keys, not passwords

Your identity is a local Ed25519 keypair. Profiles, issues, and pull requests are cryptographically signed — portable across any relay.

🔒

Public and protected chat

Every room has client-side AES-256-GCM transport. Public channels remain controller-readable for integrations; private channels and direct messages now add automatic recipient encryption beyond that key.

◎

Transparent mirror incentives

Eligible, integrity-verified mirrors may receive small community-funded mainnet-beta rewards at a self-custodial public address. Test networks require explicit development configuration; selection and payment are never guaranteed.

🌐

Federated by design

Anyone can run a relay node, Matrix- and Mastodon-style. No company sits at the center of the network — or owns its leaderboards.

⑂

Signed history in Git

Issues and PRs are append-only signed events that can live as files inside the repository itself — your project's history travels with the code.

01Your machine is the server

When you publish a repository, ForkMesh doesn't upload your packfiles anywhere. Your desktop node can expose its read-only mirror gateway through a proxied Cloudflare Tunnel. The routing service performs signed health and integrity checks, selects an available origin, and streams normal clone and browse traffic over HTTPS while the public URL stays unchanged: 

git clone https://forkmesh.com/forkmesh/forkmesh

The relay never becomes the source of truth for Git bytes. If it became unavailable, each current local mirror would still retain its own repository copy; discovery and collaboration services would need another relay or direct node access.

02Identity you own

There is no account form before exploring the world as a guest. Registering a user account requires an email, password, and email verification. The desktop node generates a local Ed25519 identity, and that key signs repository and collaboration metadata; the private signing key remains on the device.

03Public and private conversations

A catalog repository can use its own scoped encrypted room. Messages are encrypted in your client with AES-256-GCM before they touch the wire. Public channels intentionally remain controller-readable so ForkBot, MCP, and webhooks can participate. Private channels and direct messages automatically add device-to-device encryption beyond the controller's room key. The relay retains only marked frames, capped at the newest 500 per room for 7 days.

04A network that pays its hosts

Mirroring helps keep open source available, and ForkMesh treats it as first-class work. A node may publish a self-custodial Solana payout address. Configurable rounds evaluate signed identity, fresh HTTPS health, integrity, abuse status, observed contribution, and wallet validity before selecting from the deduplicated eligible set using public entropy. A transparent, community-funded mainnet-beta pool can provide small incentives, but running a node never guarantees selection or payment. Test networks require explicit development configuration.

Non-custodial notice: ForkMesh does not hold or control user funds and never stores community members’ payout- or contribution-wallet private keys, seed phrases, or mnemonics. Separately, the instance owner’s encrypted local Qt signer must explicitly approve exact outgoing pool transfers. Community rewards are incentives, not investments or promised returns.

05Signed issues and pull requests

Collaboration history shouldn't live in a proprietary silo either. ForkMesh issues and PRs are signed, append-only events that can be represented as files inside the repository. A PR carries a patch — and an optional git format-patch commit series — so it can be submitted with no push access, no fork, and no branch at all; it can also ride a real branch when a contributor has one. Every comment and review is signed too, each bound to its own PR: 

forkmesh-pull-event-v1
<author pubkey>
<ts>
sha256hex(title + NUL + base + NUL + head + NUL + patch + NUL + commits)

When a maintainer merges, ForkMesh runs a real git merge whenever there's a resolvable commit behind the PR, falling back to replaying the stored patch when there isn't — and the accepted PR, with its whole discussion thread, is committed straight into the repository on its own branch. So the conversation around your code travels with every retained copy of that repository branch.

06No center to capture

Relays are federated. The hosted mainnode offers conveniences — repository catalogs, encrypted rooms, mirror-health indexing, public reward metadata, leaderboards — but it owns none of them by right. Anyone can run their own. The network is a mesh, not a hub, so it does not rely on any one operator.

ForkMesh is a Git app first. Chat, community incentives, and discovery exist to support repositories, mirrors, and the maintainers who keep them alive.

Where we are today

ForkMesh is past its prototype stage. forkmesh.com and app.forkmesh.com run in production on self-hosted core nodes with a runner tier, and signed desktop releases ship for Linux, macOS, and Windows. Live file browsing and clone need at least one healthy mirror online. The routing service stores discovery and health metadata, not repository bytes. The direct HTTPS gateway is read-only; push and administrative operations remain separate from browse and clone traffic. Private replicas use opaque client-encrypted archives and fail closed when the requesting owner is not authorized.

But the foundation that matters is already standing: real Ed25519 identity, real Git mirroring, real encrypted rooms, a non-custodial mainnet-beta reward program, and a real federated relay. Everything from here is building outward from independently operated components that reduce reliance on any one host when current mirrors and replacement coordination remain available.
