Direct messages

Direct messages automatically add device-to-device encryption beyond the controller's room key.

Feature 48 of 72FeatureChat & private sharing3 min read

Why it matters

Direct messages give ForkMesh a concrete mechanism for node-to-node coordination inside a repository room. Their content is automatically encrypted to known participant devices before the relay's ordinary room cipher is applied.

Project conversations often carry design, access, and coordination context, so private messages exclude the controller's room key as a passive decryption key.

How ForkMesh handles it

Each installation keeps a local X25519 private key and advertises only its public key. Each direct-message frame gets a fresh AES-256-GCM content key wrapped for known room devices, then the result is encrypted by the relay-derived room key. Up to 500 persisted frames per room remain for 7 days.

A new device can read messages sent after peers learn its public key, but cannot retroactively open messages that were not addressed to it.

Public-key discovery is automatic but not independently authenticated. An active controller can inject a recipient key; the protection excludes passive controller decryption, not an actively malicious key directory.

Where it fits

Use direct messages for protected repository-aware coordination. Use public channels when ForkBot, MCP, or incoming webhooks need controller access.
