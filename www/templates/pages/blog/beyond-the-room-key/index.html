Security update

Beyond the room key

The first ForkMesh encryption artwork captured the feeling of a private path through a living mesh. It drew only one lock. Private channels and direct messages now carry a second layer: every message gets a fresh content key wrapped to known participant devices before the controller-readable room cipher is applied.

August 28, 2026Security update7 min read

ForkMesh has always encrypted chat frames before they cross the wire. That sentence was true and still left out the fact that mattered most: who could derive the key. The original room passphrase is derived from a secret held by the controller deployment. It protects traffic and retained storage from third parties, but the controller operator can derive it.

That remains the deliberate policy for public channels. ForkBot, MCP, and incoming webhooks run on or through the controller, so a room that admits those integrations must be readable there. A private channel or direct message has a different job. It now puts a recipient-encrypted envelope inside the room cipher, removing the controller room key as a passive content-decryption key.

The short version: Public means controller-readable and integration-compatible. End-to-end means automatic device-recipient encryption with controller integrations unavailable. The label is a trust boundary, not decoration.

The first generation got the mood right

The July feature cards imagined ForkMesh as a nocturnal ecosystem: shell-like nodes, fireflies, dew-lit webs, and a dark metallic core. They made encryption feel like something carried by the mesh instead of hidden in a settings panel. They also compressed a two-party trust story into one glowing line.

A fresh key for the message, a wrap for each device

On first use, every installation creates an X25519 private key and keeps it locally: same-origin storage in the browser, application settings on desktop, and the platform secure store on mobile. Only the public key is announced in the room. There is no phrase to exchange and no encryption toggle to remember.

For each protected application frame, the sender creates a fresh 32-byte content key and encrypts the complete frame with AES-256-GCM. It derives a pairwise wrapping key for each known room device using X25519 and HKDF-SHA256, wraps the content key once per recipient—including the sender's device—and then applies the ordinary room cipher outside that envelope. Retention still works because the durable marker stays outside; protected content, sender details, attachments, edits, reactions, and thread replies stay inside.

A new device can read messages sent after other participants learn its public key. It cannot retroactively open retained messages whose content keys were never wrapped to it. ForkMesh reports that honestly instead of showing a mysteriously empty transcript or weakening the room to recover history.

Two lanes, both intentionally useful

Public channels stop at the authenticated AES-256-GCM room cipher. The controller can read and author application frames, which is what lets ForkBot, MCP, and public-channel webhooks participate. The interface labels that state Public.

Private channels and direct messages require the inner recipient envelope and fail closed on an unsealed application frame. Controller integrations are unavailable because they do not hold a participant device's private key. The interface labels that state End-to-end.

Changing a channel to Public is an explicit disclosure decision for new messages; it does not unwrap older protected history. Changing it to Private rotates the outer room key, revokes incoming webhooks, and requires recipient sealing for subsequent application frames.

The limitation belongs beside the promise

Public-key discovery is not independently authenticated; it is automatic rather than a separately verified membership directory. A controller that actively injects a new public key can make future senders treat it as another room device. A controller serving modified browser JavaScript can also read data available to that browser. The new layer protects against passive controller decryption with the room key, retained envelopes, or observed room traffic; it does not turn the controller into a harmless transport under every active attack.

Timing, message sizes, connection metadata, public device keys, and retention markers also remain visible. The protocol is not a double ratchet and does not claim post-compromise security. Compromise of one participant device exposes content keys wrapped to that device, while loss of its private key loses history addressed only to it.

The documentation now carries the same boundary

This update did more than add a new hero. The README, security policy, protocol guide, Cloudflare architecture, mobile and Qt guidance, docs landing page, feature copy, privacy copy, historical launch post, Genesis changelog, and the original private-channel design records now point to the same two-lane model. Historical documents remain historical; prominent dated notes say when their relay-readable design was superseded.

The recipient-encryption implementation and its canonical documentation landed together on main. Browser, desktop, and mobile pin the same X25519/HKDF/AES-GCM fixture, and the public-claims tests reject the old blanket language. That is the standard we want for future security work: the protocol, labels, images, limitations, and tests should change as one reviewable unit.
