Product update

Signals that lead somewhere

ForkMesh's current main branch makes a handful of operational loops more deliberate: important usage pings wait for acknowledgement, teammate follow-ups keep their context, and monitoring does less redundant work without making failures wait longer.

September 1, 2026Product update5 min read

Proof before promises drew a careful boundary around current-main work and released software. The next slice is narrower: it follows the signals developers and operators use to decide what to do next, then removes the small breaks that could make those signals disappear, restart from scratch, or slow the interface carrying them.

This post covers the 40 commits that landed on main after that post, through September 1. The signed release manifests and tags did not change in this window. Unless noted otherwise, everything below is merged on main, not evidence of a new hosted deployment or native release.

A reset alert now waits until it has been seen

ForkMesh can track the five-hour and weekly usage windows for supported coding-agent providers. When an exhausted window becomes usable again, that moment is more than a transient toast: it is the signal that paused work can continue. The desktop now records that reset as a dismiss-only usage ping, keeps it visible until the user acknowledges it, and restores an outstanding ping after the app restarts.

The persistence rules are explicit. Unacknowledged reset pings are not trimmed to satisfy the ordinary local notification-history cap. A restart raises them oldest first. Acknowledgement is written immediately, and the in-app card remains the authoritative surface even when a native notification server applies its own timeout policy. If the app was closed when the reset happened, reopening it clears the stale exhausted state and raises the deferred notice.

This does not claim that ForkMesh controls provider quotas or can predict a provider's account state independently. It makes the locally configured reset window and the desktop's reminder lifecycle less lossy.

A follow-up can stay with the work

Team briefings are more useful when the next choice continues the conversation that produced the briefing. Follow-up buttons now send their direction back into the existing agent session when that session is available. The general teammate run path also prefers the teammate's prior session before creating a new one, and shared team runs can reuse the prior shared session.

The briefing surface now exposes each teammate's status, keeps reference-style links clickable, offers a direct details view, and makes each suggested next step an action instead of a selection that still requires a separate run. Team-attributed sessions can be graded and counted for every participating teammate, not only the single-teammate case.

There is still a human gate. A follow-up button supplies a prompt to a configured agent session; it does not expand the teammate's repository permissions, silently publish a pull request, or turn a finished briefing into an autonomous loop.

Busy diagnostics yield to the interface

Operator tools are most valuable during bursts, which is exactly when they should avoid monopolizing the desktop event loop. Cloud Worker tail records now enter a bounded queue and drain in short turns—at most 24 records or roughly eight milliseconds before yielding. A deliberate backpressure response carries a narrow marker so the desktop can distinguish that expected degraded response from an unhandled Worker error; a real exception still wins and remains an error.

Network-log digest checkpoints moved off the GUI thread and preserve write order behind a single worker. Clearing logs and shutting down flush the pending digest before returning. Runtime diagnostics keep their recent lag and snapshot histories in bounded circular storage, and transcript image previews retain decoded images with their owning widget instead of leaving GUI-affine pixmaps in a process-wide cache during teardown.

The branch and header fixes around the same window are similarly practical: branch cleanup avoids detached widget access, the Team header keeps controls inside compact layouts, and tests exercise teardown, queue draining, ring-buffer order, and narrow window sizes.

Status checks spend effort where the evidence changes

The public status sampler still runs every minute, but not every input needs to be downloaded every minute. Healthy synthetic checks for the homepage, status assets, and the World's mobile bootstrap graph can now reuse a durable result for ten minutes. A failed result is retried on the next minute. Visitor-observed Worker errors and the database round trip remain minute-level signals, so the cache is not used to turn a reported failure green.

The deeper flagship-repository and installer sweeps move to six-hour intervals. Between repository sweeps, recent visitor 5xx responses on flagship repository content—including release-blob routes—still feed the flagship row within the minute sampler. The installer probe also stops launching a second fallback sweep after the router has already exhausted every eligible mirror; the scheduled failure retry owns the next attempt instead.

This is a resource-shaping change in current main, not a published uptime result. It reduces repeated asset and mirror subrequests in the implementation while preserving the documented retry boundaries. The focused status tests cover healthy reuse, one-minute failure retries, stale-result replacement, interval text, visitor-error precedence, and the no-duplicate-fallback case.

Channel context is visible where the numbers are

The optional Marketing package brings channel settings into its dashboard. Organization owners and admins can see and edit whether a channel is active, its display name, and its public profile beside that channel's aggregate reach fields, then save the set in one action. Valid HTTPS profiles can be opened directly; a saved blog profile can trigger the existing RSS refresh. Other roles see the context without receiving settings authority.

This is workflow clarity, not attribution. The package still accepts explicit metric snapshots and reads published feed data; it does not infer that a channel caused a view, publish automatically, or turn an empty metric into success.

The release line has not moved

The repository's latest manifest still verifies as v0.7.29 against the installer-embedded Ed25519 publisher key, and its checksum-list hash remains bound to the signed body. The candidate-0.7.95 manifest also verifies, but remains a Linux x86_64 candidate. Neither channel changed in this reporting window.

That keeps the availability sentence simple: durable usage pings, contextual teammate continuation, the diagnostics work, cached synthetic status probes, and inline Marketing channel controls are current-main changes. They should not be described as universally installed until a matching complete signed release or separately verified deployment carries them.
