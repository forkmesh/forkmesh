Hosting, Git & preservation

Repositories that outlive any one machine

A repository should survive any single machine, company, or account. ForkMesh keeps full copies on its core servers and on independently run mirrors, and serves them all behind one ordinary Git address.

14 features

Hosted repositories

Create a repository on the website and push to it with plain git over HTTPS, no desktop node needed. Every core server keeps a full copy, private repositories included, and you can move it to your own node later.

Read the blog post about Hosted repositories

Git over SSH

Add your OpenSSH public key and clone or push any hosted repository or fork with a git@ address. Branch protection, quotas and push records work exactly as they do over HTTPS, and your private key never leaves your device.

Import from other forges

Paste a GitHub, GitLab or Codeberg address under New repository to bring the project over. A large import that stops picks up where it left off.

Mirror to GitHub or GitLab

Keep a copy of the code, issues, pull requests and releases on GitHub or GitLab, and choose which way each of them syncs.

Desktop-node mirrors

Any desktop or server can keep a live mirror of a repository and serve it to others. Mirrors pick up new issues, pull requests and discussions as soon as they are committed; private copies on mirror nodes are encrypted archives the mirror cannot read.

Read the blog post about Desktop-node mirrors

Routing relay

The relay keeps signed discovery and health records. It stores packfiles only for repositories hosted on the core servers; everything else streams from an independent mirror over HTTPS.

Read the blog post about Routing relay

Live clone routing

git clone https://app.forkmesh.com/owner/repo is ordinary Smart HTTP. Behind that unchanged address the router picks a core or a fresh, healthy mirror whose history matches the published integrity pins.

Read the blog post about Live clone routing

Streaming transfers

Packs stream over HTTPS from the chosen core or mirror. The router passes a mirror's response through without keeping a copy.

Read the blog post about Streaming transfers

Mirror failover

When an eligible, healthy, integrity-matching mirror exists, ForkMesh can fail over behind the same public URL. Sticky routing keeps one clone exchange on one mirror.

Read the blog post about Mirror failover

Source-attested integrity

Fallback serving is checked against integrity pins attested by the source of truth, so a mirror can prove it's handing you the same history the author published.

Read the blog post about Source-attested integrity

Root-commit identity

Reported mirrors can be grouped by a signed repository root commit, independent of the local name each host chose.

Read the blog post about Root-commit identity

Headless mirror nodes

One curl … | bash command and a six-digit link code turn any Linux box or VM into a mirror node that syncs its repositories and starts serving, with no GUI required.

Read the blog post about Headless mirror nodes

Public network map

The network page shows recently verified public nodes, generalized mirror health, and only optional telemetry each operator chose to publish.

Read the blog post about Public network map

Presence done right

Bounded heartbeats, expiry, and live probes reduce stale presence while allowing the deliberately minimal real-time layer to lag.

Read the blog post about Presence done right

Signed, portable collaboration

Collaboration that lives in the repository

Collaboration records aren't rows in someone else's database. They are signed events committed into the repository itself — verifiable anywhere, hosted everywhere.

8 features

Signed

Ed25519 identity

Nodes, devices, and every collaboration event are signed with local Ed25519 keys, so you can check who wrote what yourself. Your account adds an email and password for signing in.

Read the blog post about Ed25519 identity

Signed issue events

Every issue open, comment, edit, and close is a signed event. Authorship is verifiable no matter which node — or which mirror — served you the data.

Read the blog post about Signed issue events

Pull requests from forks and branches

Push a branch to your fork, or a pr/<you>/ branch where a repository accepts contributors, and open a pull request. Pull requests between instances travel as signed patches the maintainer can verify.

Read the blog post about Pull requests from forks and branches

Everything lives in Git

Issues, pull requests, reviews, discussions, and release notes are signed files committed under .forkmesh/. Clone the repo and you own the whole project history — code and conversation alike.

Read the blog post about Everything lives in Git

Web contribution inbox

Visitors can file issues and pull requests on a mirror-hosted repository even while its owner is offline. Signed submissions wait in an inbox; the owner reviews, commits, and the mesh syncs back.

Read the blog post about Web contribution inbox

Branch-backed & patch-backed PRs

Pull requests can ride a live branch (diffs derived straight from the head ref) or carry a stored patch for cross-node and offline submissions — both merge the same way.

Read the blog post about Branch-backed & patch-backed PRs

Binary-safe patches

Patches embed binary content, so images, fonts, and other assets survive the trip and merge cleanly — with a proper placeholder and badge in the diff view.

Read the blog post about Binary-safe patches

Hidden Unicode protection

Invisible characters are stripped from every input on the web, desktop, phones, and server. A pull request whose code contains them is accepted and flagged, so you can see what is hiding.

Accounts, money & rewards

Community incentives, out in the open

Community incentives are transparent and non-custodial. ForkMesh does not hold or control user funds; for community members it stores only an optional public payout address, while wallet keys and transfer approval remain on their owners’ devices. The operator’s separate community-pool signer stays encrypted on the operator’s own device. User-owned funds, the community-funded public pool, pending allocations, and completed on-chain transfers are separate states.

One deliberate exception: if the operator enables temporary deposit addresses for world-element purchases, ForkMesh generates that address and holds its key from the moment it is created until it sweeps the payment — half to the treasury, half to online mirror nodes. During that window those specific funds are custodial and an operator compromise could move them. The store labels that option with its own custody, and paying the published pool address from your own wallet remains available and puts no key on ForkMesh.
