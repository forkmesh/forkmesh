# ForkMesh Next secrets vault

The app's variables (ADMIN_PASS, the router seed, integration tokens, and so
on) are stored in the database, encrypted under `DATA_KEY`. `DATA_KEY` is
stored only on the operator's desktop. On a node it exists only in the
app's process memory, and only while that node is unsealed.

Switches in `deploy/fleet.toml` `[app]`:

- `vault = true` (Next): the vault is on. `fleet.example.toml` defaults it
  to `false`, so generic forks keep plain systemd credentials.
- `vault_peer_unseal = true` (Next): a sealed node fetches the key from an
  unsealed core peer by itself. There is no leader and no desktop in the
  steady state.

## What is where

| Item | Where it lives |
|---|---|
| `DATA_KEY` | Desktop only: `~/projects/forkmesh/config/fleet/DATA_KEY` (one line, mode 0400; preferred) or the `DATA_KEY=` line of `secrets.env`. On a node, only in the unsealed app's memory. |
| Bootstrap credentials `RQLITE_PASSWORD`, `FORKMESH_MESH_SECRET` | systemd `LoadCredentialEncrypted=` files on each node (`/etc/forkmesh-next/creds/*.cred`, host-key encrypted). rqlite and the mesh need them before any key exists. |
| `FORKMESH_CERTSYNC_SECRET` | A systemd credential of the two certsync units only (never the app). It authorizes the TLS private-key download between cores, so the app's mesh secret cannot. Generated by `next_fleet.py init-secrets`, pushed by `next_fleet.py secrets`. Not in the vault: certsync must run on a sealed node. |
| Every other app variable in `[app] secrets` + `optional_secrets`: `ADMIN_PASS`, `MIRROR_ROUTER_SIGNING_SEED`, `MIRROR_ROUTER_PUBLIC_KEY`, `WWW_EDGE_SECRET`, `MAILTRAP_API_TOKEN`, `SENTRY_DSN` (commented out in `deploy/fleet.toml` until Next has its own DSN), `APNS_*`, `DISCORD_CLIENT_*`, `ADMIN_PATH`, `PRODUCT_ANALYSIS_*` | Encrypted rows in the rqlite table `host_secrets` (migration 0194). |
| `NEXT_DNS_API_TOKEN`, `NEXT_DNS_ZONE_ID` | **Not in the vault** (audit 2026-09-24): the only Cloudflare token can edit the whole forkmesh.com zone, so it stays on the desktop (`config/cloudflare.env`, used by `tools/next_dns.py`). The nodes' leaderless DNS reconciler (`app/host/forkmesh_host/dns_reconciler.py`) would read them from the unsealed app's memory; without them it only votes and never calls Cloudflare. Re-add them only with a token scoped to a next-only zone. |

## Format

The format is implemented in `app/host/forkmesh_host/vault_crypto.py`,
which the desktop tool and the node share.

- **Key:** `HKDF-SHA256(DATA_KEY, salt "fmnext-vault-v1", info "fmnext-host-secrets")`, used with AES-256-GCM.
- **Nonce:** a random 96-bit nonce per row, new on every sync.
- **AAD:** `"fmnext-secret-v1\0" + name`. A ciphertext opens only under its own name, so rows cannot be swapped.
- **`key_id`:** the first 16 hex characters of `SHA-256(HKDF(..., info "fmnext-key-id"))`. A node can tell a wrong key without trying to decrypt, so there is no decrypt oracle.
- **`__vault_check__`:** this row seals a fixed plaintext. Before accepting any key (from the desktop or from a peer), a node proves it against this row, using a linearizable read.
- **Fail closed:** unsealing fails if any row fails authentication.

Encryption happens **only on the desktop** (`tools/next_vault.py sync`). The
nodes only decrypt.

## Node lifecycle

1. **Start: sealed.** With `FORKMESH_VAULT=1` the unit loads only the
   bootstrap credentials. `DATA_KEY` is dropped from every source (including
   env files and `FORKMESH_VAR_DATA_KEY`). While sealed:
   - Every request answers `503 {"error":"sealed"}`. `/health` answers 200
     `{"sealed":true}`, and `/readyz` answers 503 with the reason `sealed`.
     `next_deploy`'s gate and `next_dns`'s health probe both use `/readyz`,
     so a sealed node is not ready and leaves DNS.
   - Cron and queue deliveries do not run.
   - The node's `cluster_members` row has status `sealed`. The supervisor
     never activates it, placement skips it, and it hosts no Durable
     Objects.
2. **Unseal: from a peer, or from the desktop.**
   - **Peer:** at start and every 15 s while sealed, the node asks its core
     peers over the WireGuard mesh, in rendezvous order (see "Peer unseal").
   - **Desktop:** `next_vault.py unseal` pipes the key over SSH stdin into
     `/usr/local/sbin/fmnext-unseal`, which writes it to
     `/run/forkmesh-next/unseal.sock`. The socket is mode 0600 and owned by
     forkmesh-app, and peers with any uid other than root or the app's own
     are refused.
   - In both cases the node checks `key_id` and `__vault_check__`, decrypts
     every row onto `env` (including `DATA_KEY`), and turns itself unsealed.
     Its membership row goes back to `joining`, and the supervisor then
     activates it.
3. **Reload.** After a `sync`, unsealed nodes re-read `host_secrets`
   (`fmnext-unseal --reload`). No restart is needed.
4. **Seal.** `next_vault.py seal nN` makes the node drop every vault value
   and `DATA_KEY`, and clears the app's derived-key caches. The node answers
   503 again. `--restart` (socket command `seal-restart`) also overwrites
   the dropped values' bytes and ends the process, so its memory goes back
   to the kernel; systemd restarts it sealed. The IDS lockdown uses it
   (docs/IDS.md).
5. **Quarantine** (docs/IDS.md). A node the IDS quarantined refuses every
   unseal, and its peers refuse it peer unseal. After the operator's release
   the peers keep refusing until the desktop has unsealed it once
   (`next_ids.py release` does it).

On the socket, 5 failed unseals within 60 s lock out further attempts until
the window passes. A key from a peer that fails the check does not count
toward that limit, so a broken peer cannot lock the operator out.

**Node ops** (`fmnext-app-ops verify-email <account>`): with the vault on,
the wrapper sends `ops <action> <account>` over the socket and the action
runs inside the running app. No second process ever holds the key.

## Peer unseal

A sealed node sends `POST /_vault/peer-unseal` to a peer's mesh listener
(`<wg ip>:8792`). The peer answers only when all of these hold:

- the peer itself is unsealed;
- the request carries a valid mesh HMAC (`FORKMESH_MESH_SECRET`), within a
  30 s window and with a single-use nonce;
- the requester is another node of the static `FORKMESH_MESH_PEERS` map
  (rendered into the unit), and the connection comes from **that node's
  WireGuard address**. WireGuard only accepts a source address from the peer
  holding that address's key, so this binds the request to the node's wg
  private key, which never leaves the node. nftables admits port 8792 only
  on wg0 from the core addresses;
- the requester has a fresh `sealed` row in `cluster_members`, so it is a
  live member that is actually sealed;
- the rate limits allow it: 3 per requester per minute, 20 per minute in
  total.
- the requester is not quarantined, and not released-but-not-yet-unsealed
  from the desktop (docs/IDS.md).

The request carries an ephemeral X25519 public key. The peer answers with
`DATA_KEY` encrypted to that key: its own ephemeral X25519 key, HKDF-SHA256
and AES-256-GCM, with the transcript (both node names, both public keys and
the request nonce) as AAD. A passive observer learns nothing, and neither
does anyone replaying the answer. Every answer and refusal is logged in the
journal (node, address and time, never the key).

Only a restart of **every** core node at once (or a full power loss) needs
the desktop: `next_vault.py unseal`, or the `fmnext-unseal.timer` fallback.

## Threat model

**Protects against:**

- A stolen disk, Vultr snapshot or backup of a node, or a copy of the rqlite
  database, including the nightly backups on the desktop. Every app secret
  in it is ciphertext, and the key is not in it.
- A node's credential files. `/etc/forkmesh-next/creds` no longer holds
  `DATA_KEY` or any app variable. `next_fleet secrets` removes those files
  one by one.
- Someone who holds only `RQLITE_PASSWORD` or `FORKMESH_MESH_SECRET` (the
  bootstrap credentials are on disk). Rows are useless without the key. The
  mesh HMAC alone gets nothing from a peer: the request must also come from
  the claimed node's WireGuard address, and the answer is sealed to an
  ephemeral key.
- Swapped, replayed or tampered rows. The AAD binds each row to its name,
  GCM authenticates it, and the check row plus `key_id` detect the wrong
  key.
- The key reaching disk from the app process. The unit sets
  `MemorySwapMax=0` (never paged to the swapfile or zram), `LimitCORE=0`,
  and `ProtectProc=invisible`, and the process sets `PR_SET_DUMPABLE=0` (no
  ptrace or `/proc/<pid>/mem` by the same uid, no core dump). The key never
  appears in an argv, the environment or a log.

**Does not protect against:**

- **root (or code execution as forkmesh-app) on a live, unsealed node.** It
  can read the process memory. Under peer unseal it can also impersonate
  that node to a peer, from its WireGuard address with its mesh secret, and
  be handed the key. That is the same exposure as reading its own memory,
  not a new one: a compromised live core node has the key either way.
  Rotate `DATA_KEY` after such an incident (see "Rotation").
- A compromise of the desktop, which holds the key.
- Python cannot wipe strings. After a `seal`, the old key's bytes may linger
  in freed memory until reused. Sealing removes every reference, but it is
  not a secure erase.

## Availability trade-off

A node that restarts alone is unsealed by its peers within about 15 s. If
**all** core nodes restart while the desktop is off, the site stays sealed
(503 everywhere) until the desktop unseals one node. From then on, peers
unseal each other. Keep the desktop's `fmnext-unseal.timer` running. When
every node is unsealed it only reads `/readyz` and sends no key.

## Operator commands

```sh
.venv/bin/python tools/next_vault.py status                     # sealed/unsealed per node, row names + key ids
.venv/bin/python tools/next_vault.py sync --execute             # encrypt here, upsert via any healthy node, nodes reload
.venv/bin/python tools/next_vault.py sync --prune --execute     # also delete rows no longer listed
.venv/bin/python tools/next_vault.py unseal --execute           # every node (key on SSH stdin)
.venv/bin/python tools/next_vault.py unseal n2 --execute
.venv/bin/python tools/next_vault.py unseal --if-sealed --execute   # what the timer runs
.venv/bin/python tools/next_vault.py seal n3 --execute
```

To move the key out of `secrets.env` (recommended):

```sh
cd ~/projects/forkmesh/config/fleet
grep '^DATA_KEY=' secrets.env | cut -d= -f2- > DATA_KEY && chmod 0400 DATA_KEY
# check `next_vault.py status` shows "local DATA_KEY: key_id ..." matching the rows,
# back the file up offline, then delete the DATA_KEY= line from secrets.env.
```

## Rotation (TODO)

An offline rotation exists: `tools/next_rekey.py` re-keys a backup to a new
key (every `encrypt_row` value, blind index and chat envelope; the vault is
emptied and re-sealed by `sync`), which is then loaded back with the apps
stopped. docs/REKEY.md has the procedure (written for moving Next off
production's key). An online `rotate-key` is not implemented. `sync`
refuses to write when any row was sealed under another key. Plan:

1. Generate a new key. Re-encrypt every app-level `DATA_KEY` use
   (`encrypt_row` data, blind indexes). This is an app migration, not only a
   vault change.
2. Re-seal `host_secrets` under the new key in one transaction.
3. Seal and then unseal every node with the new key.

Until then, a suspected key compromise means rotating the individual app
secrets (edit `secrets.env`, then `sync`) and treating the data encrypted
under `DATA_KEY` as exposed.
