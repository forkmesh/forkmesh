# Auto-deploy: main to the core nodes

A push to `main` that changes the served stack deploys it to the cores: the
same deploy an operator runs with `tools/next_deploy.py`, driven by a ForkMesh
Actions workflow and an agent on the operator box. It never deploys the old
Cloudflare app Workers; `.forkmesh/deploy.yml` is manual-only and refuses.
`python3 tools/next_autodeploy.py pause <reason>` or `disarm` stops it.

## Pieces

| Piece | Where | Role |
| --- | --- | --- |
| Workflow | `.forkmesh/deploy-nodes.yml` ("Deploy nodes") | queued by a push to `main` matching `on.push.paths`, or by *Run workflow*; pinned to the source node; only watches |
| Agent | `tools/next_autodeploy.py serve`, user unit `forkmesh-node-deploy.service`, installed copy in `~/projects/forkmesh/bin/node-deploy/` | decides, gates and deploys |
| Deploy tool | `tools/next_deploy.py` in a clean worktree pinned to the commit | build, upload, migrate, rolling restart |
| Alerts | `POST /api/accounts/admin-operator-alert` (`app/src/operator_alerts.py`) | admin-signed Pings and email |

**Why an agent outside the sandbox.** Workflow steps run sandboxed as
`nobody` with no access to fleet credentials, and must not get them. The
agent runs as the operator and reads fleet files in place. It trusts only
run metadata the desktop writes, writes its log into the run workspace with
`O_EXCL`/`O_NOFOLLOW`, and ends with `::node-deploy-result:: ok|fail <message>`.
The agent runs its installed copy, so a commit cannot change how it decides
before it has passed the gates of the agent already running; it then updates
itself to that commit (see *Self-update*). `python3 tools/next_autodeploy.py
install` copies `tools/next_autodeploy.py`, `next_common.py`,
`forkmesh_paths.py`, `deploy/core/render.py` and `caddy_routes.py` into
`~/projects/forkmesh/bin/node-deploy/` and writes the unit. Everything else
(`next_deploy.py`, `next_fleet.py`, `next_dns.py`, the tests) runs from the
pinned worktree or the test archive of the commit being deployed, so it is
always that commit's code.

## Where the agent finds runs

The desktop writes each run's `meta.json` under
`~/projects/forkmesh/data/actions/runs/`, but its sandbox tree (the run's
`/workspace`, where the agent writes `node-deploy.log`) goes wherever
`ActionStore::sandboxDir()` puts it: `data/actions/sandbox/`, or
`<TMP mount>/ForkMesh/actions/sandbox/` when a disk labelled `TMP` is in use
([TMP disk](../desktop/tmp-disk.md)). `running_runs` scans both, finding the
TMP disk the way the desktop does (`/dev/disk/by-label/TMP` matched against
`/proc/self/mounts`), and keeps the newest `forkmesh-run-<id>-<ms>` per run.

Before 2026-10-24 it scanned only `data/actions/sandbox/`. Once the desktop
moved sandboxes to the TMP disk that evening, the agent never saw a run:
run #7903 (`03273107bf0a`) ended "did not pick up this run within 3 minutes"
with the agent idle. An agent that sees no runs never deploys, so it cannot
take this fix by self-update; run `install` by hand once.

## Trigger

- **Only `main`** of the served repository, and only commits on the source
  checkout's `main`. Branch, pull-request and fork runs are refused. Merges
  made on the cores deploy once the source publisher brings them into the
  checkout.
- **Only served-stack paths** (`classify`):
  - *release paths* (`app/`, `office/`, `world/`, `www/public/`,
    `www/worker.js`, `www/wrangler.production.toml`, `deploy/`,
    `marketplace/packages/`, marketplace catalog files,
    `tools/rqlite_migrate.py`, `tools/next_*.py`) start an app release;
  - *roll paths* (`server/`, `deploy/core/`, `tools/mirror_gateway.py`, not
    Markdown) need a node roll. `deploy/core/` covers `render.py`,
    `caddy_routes.py` and `templates/`, so a Caddy change reaches the cores
    through the roll's `files` and `start` steps (`start` reloads Caddy)
    without a hand-run `next_fleet.py roll`.
  Tests never count. Changed paths are those of the whole push.
- The workflow's path filter is a prefilter generated by
  `python3 tools/next_autodeploy.py workflow-paths` and checked by
  `deploy/tests/test_next_autodeploy.py`.
- **Debounce:** deploy once `main` is quiet for a few seconds (10-minute cap);
  deploy the tip; every waiting run the deployed commit contains gets the
  result.
- **Pause after a deploy:** once a deploy has restarted the cores, the next
  one waits `DEPLOY_COOLDOWN_SECONDS` (5 minutes), so merges landing in that
  window ship as one deploy. A deploy that failed before restarting anything
  (gate 1 to 3) does not pause the next one, so a fix ships at once. On
  2026-10-21 ten deploys started between 13:02 and 14:22, each right after the
  one before.
- Fast-forwarding `main` to a commit first pushed on a branch queues no main
  run; merge with `--no-ff` or run `deploy --commit <sha>`.

## Gates, in order

1. **Fast-forward only.** Read each core's running revision from
   `/api/version`, locate it (deploy manifest, the commit itself, or a served
   tree signature) and refuse a rollback unless the run is a manual rollback.
   If nothing served changed, end green. If no core answers at all, treat the
   operator box as offline and wait up to 30 minutes rather than blaming a
   node. If some cores answer and others give no HTTP answer at all, ask the
   silent ones again every 30 seconds for up to 5 minutes before failing: on
   2026-10-18 the operator box lost its route for about three minutes while
   gate 1 was asking n2, the network was back by the time n3 and n4 were
   asked, and the deploy of `6b5522ccc12f` failed although n2 never stopped
   serving the other cores. A core that answers with an HTTP error still
   fails the gate at once.
2. **Tests** from a clean `git archive` in a no-network sandbox with no home:
   a must-pass set (`app/tests/host/test_host_e2e.py`, `deploy/tests`, host
   shim, request guard, apps e2e, timer, desktop and operator-alert pings,
   the `security` suite of `tools/run_critical_tests.py` and the
   destructive-delete scanner), `go test ./...` in `server/`, plus *no new
   failures* in `app/tests/host` against the deployed commit (baseline
   cached). Must-pass entries may be files, folders or single test ids. Files
   run in parallel at low priority while the build and upload proceed; the Go
   tests run beside them in the same sandbox with the host's Go toolchain
   bound read-only (`GOTOOLCHAIN=local`, `GOPROXY=off`, a per-run
   `GOCACHE`). Go is found on the agent's `PATH`, then in `/usr/local/go`,
   `/usr/lib/go`, `~/go` or `~/.local/go`; without it every deploy fails at
   this gate rather than skipping the Go tests.
3. **Build** in a fresh detached worktree.
4. **Deploy:** upload, migrate, then a rolling restart one core at a time
   (the first chosen per release), each gated on `/readyz` (never ready while
   sealed) and the running revision before the next one restarts, with
   per-node rollback.
5. **Verify** on each node: `/readyz`, `/api/version`, the node name's
   `/readyz`, `/dashboard`, `/login`, and the World deploy marker, retrying up
   to 2 minutes.

## Node rolls

After the release passes (or for a roll-only push), the agent runs
`python3 tools/next_fleet.py roll --execute` from the pinned worktree under
the deploy lock: one core at a time, drain, wait the DNS TTL plus 30 s
(`ROLL_DRAIN_MARGIN_SECONDS`, 90 s in all), install `daemon,files,start`,
check readyz, units and IDS, undrain, stop at the first failure. Roll paths
are counted since the last successful roll, so a skipped roll is caught up.
When `server/` changed, it then runs `roll-runners --idle-wait 0`, which
never restarts a runner with active job scopes; busy runners are retried every
10 minutes. Failures Ping and email and are kept in `state.json` until
`next_autodeploy.py ack-roll`. Create `<fleet config>/autodeploy/manual-roll`
to only report that a roll is needed.

By hand: `python3 tools/next_fleet.py roll [nN ...] [--mail] --execute`,
`roll-runners [rN ...] --execute`, then `ack-roll`.

## Self-update

Before 2026-10-21 the agent kept the code it was installed with until an
operator re-ran `install`, so a change to the agent (such as the 5-minute
pause after a deploy) never ran on its own.

Now, once the agent is idle, it compares its installed files with those of
the last commit whose deploy passed gate 2 and ended green (`state.json`
`tested`, written for `auto` and `manual` deploys, never for `rollback`).
The comparison is by git blob hash (`git hash-object` of each installed file
against `git rev-parse <commit>:<path>`), never by mtime. If they differ:

1. **Only when idle:** no deploy running, no run queued, no runner-roll
   retry running, auto-deploy armed. A queued run is deployed first; the check
   runs again after it. While it runs and while it restarts, the agent
   attaches no new run, so the restarted agent picks up every waiting run from
   the run folders.
2. **Once per set of files:** the hash of the commit's agent files is
   recorded in `state.json` `selfUpdate` before anything runs. The same files
   are never tried again, at that commit or a later one; changed files on a
   later commit get one new attempt.
3. **Under the deploy lock** (`wait=0`; a busy lock retries a minute later).
4. **Stage and check:** in the pinned worktree at the commit, run
   `install --stage <cache>/node-deploy/agent-stage`, then
   `<stage>/next_autodeploy.py self-check`, which imports every module from
   the staged folder, builds the agent and its notifier as `serve` does, and
   prints `next_autodeploy self-check ok`. A failure stops here and nothing
   installed changes.
5. **Install:** copy the current files and unit into
   `bin/node-deploy.previous/`, run `install --no-restart` from the worktree,
   check the installed hashes match the commit, arm a watch
   (`systemd-run --user`, unit `forkmesh-node-deploy-watch-<hash>`, in 180 s,
   running the previous copy's `self-update-watch`), then
   `systemctl --user restart --no-block forkmesh-node-deploy.service`.
6. **Confirm:** the new agent's `serve` marks `selfUpdate` `ok`, records
   `state.json` `agent`, and Pings "Node deploy agent updated to <rev>".
7. **Failure:** a failed stage, check, install, watch or restart puts the
   previous files and unit back where they were already replaced, marks
   `selfUpdate` `failed`, logs `self-update: FAILED`, and Pings and emails
   "Node deploy agent update to <rev> failed". If the new agent has not
   confirmed after 180 s, the watch restores the previous copy, restarts the
   unit, and alerts the same way. Nothing is deleted.

After a failure, fix the agent on `main` (new files get a new attempt) or run
`install` by hand. `status` shows `selfUpdate` and `agent`.

`tools/forkmesh_paths.py` is not a served path, so a push that changes only
it starts no deploy; the agent takes it with the next green deploy.

## The website Worker

After a good deploy the agent compares the forkmesh.com Worker's
`x-forkmesh-deploy-fingerprint` with the hash of the target's `www/` tree and,
if they differ, runs `npx wrangler deploy --config wrangler.production.toml`
from the pinned worktree with Node 22 and credentials from
`config/fleet/cloudflare.env`. The node roll runs before the website step, so
a website failure never skips a roll.

## Safety

- **One deploy at a time:** `<fleet config>/deploy.lock` (`flock`) is taken by
  every `next_deploy --execute`, `next_fleet roll` and `install`, and by the
  agent (deploys, runner-roll retries and its self-update), which passes it to
  children as `FMNEXT_DEPLOY_LOCK_FD`.
- **Kill switch:** auto-deploy needs `autodeploy/armed` and no
  `autodeploy/paused` (`pause`, `resume`, `disarm`). Manual deploys still work.
- **Manual triggers:** `deploy --commit <sha|main> [--skip-tests]`,
  `rollback --rev <rev> [--run-tests]` (also the way past gate 1 after a
  history rewrite), *Run workflow*, the desktop's Deploy app button, and
  `next_deploy.py rollback nN --execute`.
- **Alerts:** every failed or refused deploy Pings admins; a second failure in
  a row also emails them.
- **Weak networks:** probes retry dropped connections; uploads resume a
  dropped scp.
- **rqlite tunnel:** `next_deploy.open_rqlite_tunnel` picks the first loopback
  address that accepts connections (`127.0.0.1`, `::1`, `127.0.0.2`) so a
  local firewall dropping one address does not block deploys; errors end with
  a concrete `Fix: …`.
- `python3 tools/next_autodeploy.py status` prints the switch, lock holder,
  last deploy and failure, pending rolls and live revisions.

## World deploy notice

`next_deploy.py` writes the `world_deploy_status` row (`deploying`, `ready`,
`failed`) for whole-fleet commands; the World client polls
`/api/world/deploy-status` and offers a refresh. Status alerts are suppressed
while deploying and for 5 minutes after.

## Install

```sh
python3 tools/next_autodeploy.py install
python3 tools/next_autodeploy.py status
```

The unit starts disarmed. After the first install the agent updates itself
(see *Self-update*); an install from before 2026-10-21 has no self-update, so
run `install` once by hand to get it. Gate changes, such as the Go tests and
the security must-pass set added on 2026-10-15, apply from the deploy after
the one that brought them. `install --stage <dir>` copies the files only;
`install --no-restart` installs without restarting the unit. If runs never
report a result, compare the installed copy with `tools/`.

## Restarts without 502s and 503s

On 2026-10-21 users saw "Notes are unavailable: HTTP 502" and 503s from
other pages while `main` was deploying. Nothing was wrong in the App code:
the rollout itself took cores away from clients that were still using them.

- `next_deploy restart` restarted the canary and then the other two cores
  together, still in DNS. For 10 to 20 s two of three cores had no App
  behind Caddy: Caddy answered 502 once `lb_try_duration` (10 s) ran out, and
  the App answered `503 {"error":"sealed"}` until it was unsealed. The
  desktop saw a WebSocket 502 at 13:10:29, during the n4/n2 restart of
  `99fa98f28091`.
- `next_fleet roll` removed a core's A/AAAA records (TTL 60 s) and started
  its install about 6 s later, so clients still holding the address hit the
  restart. The desktop saw a 502 at 13:22:09, 31 s after n4 was drained for
  the roll of `0b105afa2be5`.

What changed:

- Restarts go one core at a time (`tools/next_deploy.py` `restart`); each
  must pass `/readyz` and report the new revision before the next starts.
- A roll waits out the DNS TTL plus 30 s after the drain, before the core
  restarts (`tools/next_fleet.py` `roll`).
- Caddy keeps a request waiting for the local App for up to
  `APP_UPSTREAM_TRY_SECONDS` (30 s, `deploy/core/render.py`) instead of 10 s,
  which covers an App restart. If the App is still unreachable, the shared
  names answer `{"error":"upstream_unavailable"}` with `Retry-After: 5` (the
  `upstream_errors` snippet). The status stays 502 or 504, because the
  forkmesh.com Worker falls back to the per-node names only on those
  (`www/worker.js` `APP_FALLBACK_STATUSES`). The Caddy install check allows
  `CADDY_INSTALL_MAX_TIME` (35 s) per request, so a fresh core's `/readyz`
  is not cut off while Caddy waits for the App.
- The Notes page retries a failed read 3 times (0.5, 1.5 and 4 s), as
  `fetchJson` already did, and shows "ForkMesh is restarting" rather than
  "HTTP 502".

What is still exposed: a browser keeps reusing an HTTP/2 connection to a
drained core, so DNS does not move it. For those clients the 30 s Caddy wait
and the client retries are what hide the restart.
