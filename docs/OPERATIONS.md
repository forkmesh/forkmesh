# ForkMesh Next operations runbook

How to bring up, deploy, check and tear down the Next fleet: 3 core nodes
(`fmnext-core-1..3` = `n1..n3`) and 1 runner (`fmnext-run-1` = `r1`) on
Vultr, with DNS on Cloudflare. The design is in `docs/PLAN.md`; node files
come from `deploy/core/render.py`.

Every tool here does a **dry run by default** and prints what it would do.
Nothing changes without `--execute`. Run all commands from
`~/projects/forkmesh/src`.

## 1. What the operator provides

All of it lives in `~/projects/forkmesh/config/fleet/` (mode 0700, files 0600)
on the operator box. The tools never print these values or pass them on a
command line.

| File | Contents | Notes |

The same account holds **unrelated production instances** (`tradeskie-production`, `Blt`, `mirror35`..`mirror38`). `next_fleet.py` only touches instances whose label starts with `fmnext-` **and** that carry the `forkmesh-next` tag. Better: a Vultr sub-user limited to instances. |

The desktop can write it from Settings → Cloud. |

Meant for a token scoped to **Zone → DNS → Edit on forkmesh.com** only. ## 2. Bring up the fleet

The four instances already exist (created 2026-09-23: `vc2-1c-1gb`, ewr,
Debian 13, tag `forkmesh-next`). `create-*` adopts an existing instance by
label, so these commands are safe to re-run.

```sh
# 0. Look before touching anything (read-only API calls).
python3 tools/next_fleet.py plans
python3 tools/next_fleet.py list                      # only fmnext-* tagged forkmesh-next

# 1. Instances (adopted if they exist) and the fleet file.
for n in 1 2 3; do python3 tools/next_fleet.py create-core $n --execute; done
python3 tools/next_fleet.py create-runner 1 --execute
python3 tools/next_fleet.py fleet-toml --execute     # deploy/fleet.toml from fleet-instances.json

# 2. Secrets (generated locally, 0600, never printed).
python3 tools/next_fleet.py init-secrets --execute

# 3. Base system and WireGuard keys on every core node. Each private key is
#    generated on its node and never leaves it.
for n in n1 n2 n3; do python3 tools/next_fleet.py install $n --steps base,wireguard --execute; done
python3 tools/next_fleet.py fleet-toml --execute     # now with the WireGuard public keys
git add deploy/fleet.toml && git commit -m "fleet: WireGuard keys"

# 4. rqlite, the rendered files, secrets, and start. Any order: there is no
#    ACME issuer or leader to start first; rqlite forms the cluster once all
#    three are up (-bootstrap-expect 3).
for n in n1 n2 n3; do
  python3 tools/next_fleet.py install $n --steps rqlite,files,secrets,start --execute
done

# 5. DNS: app/world (production and next) -> all three cores, nN.next -> each
#    node; A records, plus AAAA for nodes with public_ipv6.
python3 tools/next_dns.py ensure            # check the plan first
python3 tools/next_dns.py ensure --execute

# 6. First app release: build, upload, migrate (through any healthy node), then
#    a rolling start.
#    With the vault on, fill it before the first start (the migration creates
#    host_secrets): build + upload + migrate, then sync, then restart (which
#    unseals each node with DATA_KEY on SSH stdin before gating it).
python3 tools/next_deploy.py all            # plan
python3 tools/next_deploy.py build --execute
python3 tools/next_deploy.py upload --execute
python3 tools/next_deploy.py migrate --execute
python3 tools/next_vault.py sync --execute  # encrypt here, rows via any healthy node (docs/VAULT.md)
python3 tools/next_deploy.py restart --execute
python3 tools/next_vault.py status          # every node "unsealed, ready"

# 7. Shared certificate: the rendezvous-first live core issues app.next and
#    world.next once DNS resolves (Caddy retries on its own); the others serve a
#    local self-signed certificate (so DNS health keeps them out) until their
#    fmnext-cert-sync.timer (every 5 min) pulls the real pair. To hurry it:
for ip in <n1-ip> <n2-ip> <n3-ip>; do
  ssh -i ~/projects/forkmesh/ssh/fleet/next_fleet_ed25519 root@$ip systemctl start fmnext-cert-sync.service
done

# 8. The Go daemon (role core: no agent jobs, no Actions), once the App answers.
for n in n1 n2 n3; do python3 tools/next_fleet.py install $n --steps daemon --execute; done

# 9. Runner: base system, files and firewall, then the daemon (role runner).
python3 tools/next_fleet.py install r1 --execute
python3 tools/next_fleet.py install r1 --steps daemon --execute
```

Homepage: `tools/next_autodeploy.py` deploys `forkmesh-www` (forkmesh.com)
with `www/wrangler.production.toml` ([auto-deploy](deploy/auto-deploy.md)). By
hand:

```sh
cd www
npx wrangler secret put WWW_EDGE_SECRET --config wrangler.production.toml   # same value as WWW_EDGE_SECRET in secrets.env
npx wrangler deploy --config wrangler.production.toml
```

A plain `npx wrangler deploy` fails: `www/wrangler.toml` has no Worker name
([CUTOVER.md](CUTOVER.md), "forkmesh-next-www deleted again").

Operator-box services (copy them, they are not installed for you):

```sh
install -m 0644 deploy/operator/fmnext-backup.service deploy/operator/fmnext-backup.timer \
  deploy/operator/fmnext-unseal.service deploy/operator/fmnext-unseal.timer \
  ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now fmnext-backup.timer fmnext-unseal.timer
loginctl enable-linger "$USER"
```

The DNS health failover loop runs on this box too (section 4, "DNS health
failover"):

```sh
install -m 0644 deploy/operator/fmnext-dns-health.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now fmnext-dns-health.service
```

It is installed and enabled on the operator box since 2026-09-24. The core
nodes also vote on health (section 4, "DNS health"), but they hold no
Cloudflare token and never change DNS. Never let both change records: keep
`[dns] reconciler` at `dry`/`off` while the desktop loop runs.

## 3. Verify

```sh
K=~/projects/forkmesh/ssh/fleet/next_fleet_ed25519
# rqlite: 3 reachable voters, one leader (ask any core).
ssh -i $K root@<any-core-ip> "curl -fsS -K /etc/forkmesh-next/rqlite.curlrc 'http://127.0.0.1:4001/nodes?nonvoters'"
# Every node serves the shared names with a valid certificate and is ready.
for ip in <n1-ip> <n2-ip> <n3-ip>; do
  curl -fsS --resolve app.next.forkmesh.com:443:$ip https://app.next.forkmesh.com/readyz
  curl -fsS --resolve app.next.forkmesh.com:443:$ip https://app.next.forkmesh.com/api/version
  curl -fsSI --resolve world.next.forkmesh.com:443:$ip https://world.next.forkmesh.com/
done
curl -fsS https://n1.next.forkmesh.com/readyz               # per-node name
python3 tools/next_dns.py status                            # the A and AAAA records
python3 tools/next_dns.py health-once                       # one probe round from here (dry run)
curl -fsS https://next.forkmesh.com/api/home-availability   # homepage -> App
```

Then work through the live checks in `docs/PLAN.md` ("Verification"): sign
up, log in, WebSockets across two nodes, push and clone, and killing the
leader mid-write.

## 4. Routine operations

- **Deploy**: `python3 tools/next_deploy.py all --execute`. Migrations run
  through the first node with a healthy rqlite (rqlite forwards the writes);
  the restart goes one node at a time, in an order that rotates per release
  (only the app restarts, so the rqlite leader's node is not special, and no
  core is always first). Each node is gated on
  `127.0.0.1:8080/readyz` and on `/api/version` reporting the new rev, then
  on Caddy serving `https://nN.<domain>/readyz` on loopback. Caddy gets up to
  30 s (a crash restart under `Restart=on-failure` fits in it); if it still
  does not answer, the gate restarts Caddy once and waits 30 s more. Each
  route reload is bounded (`timeout 60 systemctl reload caddy`) and followed
  by the same wait. A node that fails the gate goes back to its previous
  release, and the rollout stops there.
- **Half-activated nodes (fixed 2026-09-24)**: `Ssh.run` runs every script
  under `bash -euo pipefail`. When Caddy 2.6.2's reload failed, the old
  activate script exited right after switching `current`, before the app
  restart and without rolling back. The node then served the old app under
  the new `current`, and `next_deploy restart` was the only fix. Now:
  - the activate and rollback scripts turn off `-e`/`pipefail`, ignore
    SIGHUP/SIGPIPE (a dropped SSH session no longer kills them half-way), and
    hold `/run/fmnext-activate.lock`;
  - every step can fail without skipping the app restart;
  - after each activation, the tool reads, under the same lock, what
    `current/BUILD_REV` says and what the running app's `/api/version`
    reports. A node counts as activated only when both are the new rev.
  - If they differ, or the session was lost, it activates that node once
    more, then stops with the state it found.
- **Rollback one node**: `python3 tools/next_deploy.py rollback n2 --execute`.
- **Change node files** (units, Caddyfile, firewall) after editing
  `deploy/core/templates` or `deploy/fleet.toml`: run
  `install nN --steps files,start --execute` on one node at a time. The
  files step puts the current release's `app-routes.caddy` and
  `world-routes.caddy` back after writing the rendered ones (those have no
  dist, so no static routes or `_headers`); the IDS expects both paths.
- **Caddy binary**: see "Caddy version" below.
- **Rotate a secret**: edit `secrets.env` (or `cloudflare.env` for the DNS
  token), then `python3 tools/next_vault.py sync --execute`: it re-encrypts
  here and the unsealed nodes reload without a restart. For the bootstrap
  credentials (`RQLITE_PASSWORD`, `FORKMESH_MESH_SECRET`) run
  `secrets nN --execute` on each node and restart the affected units. For
  `WWW_EDGE_SECRET`, update the Worker secret after the core. `DATA_KEY`
  itself is rotated only offline, with the apps stopped: docs/REKEY.md
  (`tools/next_rekey.py`).
- **Vault**: `python3 tools/next_vault.py status` shows sealed/unsealed per
  node and the row names with their key ids (never values). A restarted node
  is unsealed by its peers over the mesh within about 15 s
  (`vault_peer_unseal`); the desktop `fmnext-unseal.timer` only acts when a
  node stays sealed (every node restarted at once). By hand:
  `next_vault.py unseal [nN] --execute`; take a node out: `seal nN --execute`.
- **Node ops** (`fmnext-app-ops verify-email <account>` as root on a node):
  with the vault on it runs inside the running app over the unseal socket,
  so the node must be unsealed.
- **Backups**: the nightly `fmnext-backup.timer` runs
  `tools/next_backup.py run --execute`, which pulls
  `GET /db/backup?compress` from whichever node currently holds rqlite's
  Raft leadership (a desktop-side read of rqlite's consistent snapshot, not a
  node role) over an SSH tunnel into
  `~/projects/forkmesh/data/fleet/backups/rqlite-<UTC>.sqlite3.gz`. A backup is
  kept only after it passes `PRAGMA integrity_check` and the table counts.
  Retention is 7 daily + 4 weekly, and only files named
  `rqlite-YYYYMMDDTHHMMSSZ.sqlite3.gz` are ever deleted. To check one by
  hand: `python3 tools/next_backup.py verify <file>`. To restore, load the
  file into a fresh cluster with rqlite's `/boot` or `.restore`.
- **Certificates** (leaderless, `deploy/core/certsync.py`): nothing to move.
  `journalctl -u fmnext-cert-sync` on a node shows the live peers, the issuer
  per name (rendezvous-first live node) and the mode (`files` = serving the
  shared pair, `acme` = this node is renewing through Caddy, `internal` = no
  pair yet). The issuer switches to `acme` only when the freshest pair held by
  any node is within 30 days of expiry (or missing); the next sync after
  Caddy renews exports it and every node pulls it. If the issuer dies, the
  next node in rendezvous order renews.
- **Cron** (leaderless): the per-minute cron coordinator (every phase,
  including all status probes) runs on a different live node each minute,
  round-robin, handed over 45 s into the minute. `journalctl -u forkmesh-app
  | grep 'cron minute'` shows which minutes ran here; the `host_cron_runs`
  table has all nodes (slot, node, phases). Keep the node clocks in sync
  (Debian's systemd-timesyncd is on by default): ownership is computed from
  each node's clock.
- **DNS health** (leaderless, `app/host/forkmesh_host/dns_reconciler.py`):
  every unsealed node probes every core node every 30 s and writes its votes
  to `dns_health_votes`; the node chosen for each 30 s interval changes the
  `app.next`/`world.next` A records only when a majority of live voters
  agree, never empties a set, never touches `nN.next`, and at most once per
  5 minutes cluster-wide (`dns_reconciler_state.last_change_ms`). Acting
  needs the vault values `NEXT_DNS_API_TOKEN`/`NEXT_DNS_ZONE_ID`, which are
  deliberately **not** in the vault (audit 2026-09-24: the only token edits
  the whole forkmesh.com zone). Until a token scoped to a next-only zone
  exists, the fleet runs `[dns] reconciler = "dry"`: nodes vote and log
  (`journalctl -u forkmesh-app | grep dns:`, and `dns_health_votes`), log
  once that the token is missing, and never call Cloudflare; the desktop
  `tools/next_dns.py` stays the way DNS changes. `"on"` only matters once
  such a token is in the vault; `"off"` stops the votes (re-render with
  `install nN --steps files,start`). The node reconciler manages only the
  `next.*` names. The production names fail over only through the operator
  box loop ("DNS health failover" below).
- **DNS health failover** (`tools/next_dns.py health-loop --execute`, the
  `fmnext-dns-health` user unit on the operator box, section 2):
  - **Names:** `app.forkmesh.com`, `world.forkmesh.com`, `app.next` and
    `world.next`. Each carries one A record per member node and one AAAA
    record per member node with `public_ipv6`. `nN.next` records are set
    only by `ensure`.
  - **Probe:** every 30 s the loop sends a TLS-verified `GET /readyz` for
    `app.forkmesh.com` to each core's IPv4 address. A sealed, quarantined or
    locked-down node answers 503 or nothing, so it counts as failed. For nodes
    with IPv6 the loop also probes the IPv6 address and logs the result
    (`v6 ok`/`v6 FAIL`). That result does not drive decisions.
  - **Rules:**
    - A node that fails 3 probes in a row leaves every name, A and AAAA.
    - It returns after 2 minutes of continuous health.
    - The last member is never removed. A healthy node can still be
      re-added while the last member is failing (until 2026-10-04 that case
      blocked every add).
    - A round in which every core fails counts for no node. A dead link on
      the operator box looks just like that, so the loop logs "this box looks
      offline" and leaves DNS alone. On 2026-10-04 a 15-minute outage on the
      box nearly removed n1 ([deploy/auto-deploy.md](deploy/auto-deploy.md)).
    - At most one change is made per 5 minutes.
    - A name whose members have no IPv6 keeps its AAAA records untouched,
      so a set is never emptied.
  - **Where the rules live:** `HealthState` in `tools/next_dns.py`, with the
    constants and `plan_set` in `app/host/forkmesh_host/dns_rules.py`. The
    state file is `config/dns-health.json`.
  - **Drain for maintenance:** run `next_dns.py drain nN --execute` before
    rebooting or reworking a node. It removes the node from every name
    immediately (it refuses to remove the last member) and marks it `held`,
    so the loop never adds it back. `next_dns.py undrain nN --execute`
    clears the hold. The loop then re-adds the node once it has been healthy
    2 minutes and 5 minutes have passed since the last change. Wait out the
    60 s TTL between the drain and the work.
  - **Logs:** `journalctl --user -u fmnext-dns-health`.
  - **Config changes:** the loop re-reads `deploy/fleet.toml` every round.
    It runs the code in `~/projects/forkmesh/src` (main), so restart it
    after `next_dns.py` changes:
    `systemctl --user restart fmnext-dns-health`.
  - **Negative caching:** `forkmesh.com`'s SOA minimum is 1800 s. A resolver
    that asked for AAAA before the records existed keeps its empty answer for
    up to 30 minutes.
- **IPv6** (since 2026-09-24): n1–n3 have Vultr IPv6. Each node's address
  is the `ipv6` of its label in `fleet-instances.json` (loaded as
  `public_ipv6`; docs/deploy/README.md, Node addresses), and the node gets it from the
  router advertisement: cloud-init writes `iface enp1s0 inet6 auto` and
  dhcpcd applies it. Caddy, sshd and WireGuard listen on both families.
  - **Firewall:** the nftables input chain (`table inet`) applies the same
    rules to IPv6. Only 22, 80, 443/tcp, 443/udp and WireGuard are open, and
    ICMPv6 is accepted.
  - **Service-user egress:** the IDS logs unusual outbound connections of
    the service users over IPv6 as well.
  - **Lockdown:** the IDS table accepts ICMPv6, so neighbour discovery keeps
    working, and it drops IPv6 SSH when `ssh_allow` is set, because
    `ssh_allow` is IPv4 only.
  - **fail2ban:** it uses the Debian default `banaction = nftables` (an
    `inet` table, both families). The `start` step restarts it after
    reloading nftables, because `flush ruleset` drops its table.
  - **Enabling IPv6 on a node:**
    1. Drain the node from DNS.
    2. Run `next_fleet.py enable-ipv6 nN --reboot --execute`. Vultr reboots
       the instance when IPv6 is enabled. The tool tells the IDS first,
       records the address in `fleet-instances.json`, and waits for the
       address and `/readyz`.
    3. Run `next_fleet.py fleet-toml --execute` and commit it. It now keeps
       `[production]`.
    4. Run `next_dns.py ensure --execute`, then undrain the node.
  - The runner `r1` has no IPv6: it has no public name, and its job firewall
    already refuses private IPv6 ranges.
- **Add a core node**: `python3 tools/next_fleet.py add-core --execute`, or
  the desktop's Network → Hosts → **Add core node**. It creates the VM, joins
  the mesh and rqlite (as a non-voter while there are 3 voters), installs the
  served release and every repository, and adds the node to DNS only once it
  is healthy. It resumes after a failure. See
  [deploy/README.md](deploy/README.md#adding-a-core-node). A core that is new
  to `dns-health.json` starts held out of DNS until `next_dns.py undrain`.
- **Remove a core node**: `python3 tools/next_fleet.py remove-core nN
  --execute` (dry run without `--execute`), or **Remove…** on the core's
  row in Network → Hosts. Any core can go, `n1` included: no core is the
  main one ([deploy/README.md](deploy/README.md#no-fixed-main-node)). It is
  refused below 3 cores or 3 healthy voters; when a non-voter core exists,
  it is promoted to a voter first. See
  [deploy/README.md](deploy/README.md#removing-a-core-node).
- **Replace a core node**: add one, then remove the old one
  ([deploy/README.md](deploy/README.md#replace-a-core-add-one-then-remove-one)):
  `add-core --execute`, merge `fleet/add-core-nN`, `remove-core n1
  --execute`, merge `fleet/remove-core-n1`. The older one-shot
  `replace-core n1 --new n4 --execute` still exists but leaves the peers'
  re-render, DNS and the fleet file to you.

- **Switching a running fleet to leaderless cron/DNS/certificates** (the
  release that adds migration 0196, one-time):
  1. `next_deploy.py all --execute`: migrates (0196: `host_cron_runs`,
     `dns_health_votes`, `dns_reconciler_state`) and restarts the apps. Until
     every node runs the new release the old nodes still pin the cron to the
     rqlite leader, so a minute may run twice during the rollout; it settles
     as soon as the last node restarts.
  2. Per node, one at a time: `next_fleet.py install nN --steps files,start
     --execute`. This retires `fmnext-cert-export.*` / `fmnext-cert-pull.*` by
     name, runs `fmnext-certsync prepare` (Caddy's tls includes from the
     certificate the node already has, so it keeps serving it), and starts
     `fmnext-certsync.service` + `fmnext-cert-sync.timer` everywhere.
  3. DNS: nothing to do. The node reconciler runs `dry` (votes only; no
     token on the nodes), so keep using `tools/next_dns.py` (or the optional
     desktop loop) for record changes.

### Signup challenge (Cloudflare Turnstile)

Production puts `/signup*` behind a Cloudflare zone WAF challenge. Next's
hostnames are DNS-only (the traffic never reaches Cloudflare), so the App
checks a Cloudflare Turnstile token itself (`app/src/turnstile.py`).

- **The widget**: in the Cloudflare account under Turnstile, named
  `forkmesh-next-signup` (managed mode, domains `app.next.forkmesh.com` and
  `next.forkmesh.com`). Its public site key is `TURNSTILE_SITE_KEY` in
  `app/wrangler.toml` [vars]. The secret is `TURNSTILE_SECRET_KEY`, which
  goes in `secrets.env` and the vault (`[app] optional_secrets` in
  `deploy/fleet.toml`).
- **What is gated**: `POST /api/accounts/signup` (widget on `/signup`, action
  `signup`, bound to that page view's signup claim) and
  `POST /api/accounts/forgot-password` (widget on `/forgot-password`, action
  `password-reset`). The node registrations `/api/accounts/reserve` and
  `/finalize` are not gated: desktop and headless installers can't render
  the widget, and those requests are Ed25519-signed. A new name claim
  instead has a per-IP limit (5 per hour). The mobile and native apps open
  `/signup` in the browser, so users solve the widget there. A client that
  posts the API directly gets 403 `turnstile_required` with a
  `challengeUrl`.
- **Stale page**: each `GET /signup` issues a new claim cookie. A token whose
  cdata belongs to an earlier page view (the visitor reloaded `/signup` or
  opened it in a second tab, then submitted the older one) is refused with
  403 `turnstile_stale_page`, and the page tells them to reload. Before
  2026-10-13 this was `turnstile_failed`, whose "Try it again" could never
  pass because the old tab keeps the old cdata.
- **Fail closed**: without the secret the nodes answer 503
  `turnstile_unavailable` on both forms. A siteverify timeout (5 s), a
  transport error or a non-200 answer gets the same response. The first
  occurrence pings the admins through the error log (path
  `/api/accounts/signup`, method `SIGNUP`). Check the node egress if
  siteverify fails: `challenges.cloudflare.com:443` is a public HTTPS name
  that the egress guard allows.
- **Rotate the secret**: in the Cloudflare dashboard (Turnstile →
  `forkmesh-next-signup` → Rotate secret key), put the new value in
  `secrets.env` as `TURNSTILE_SECRET_KEY`, then run
  `python3 tools/next_vault.py sync --execute`. The unsealed nodes reload it
  without a restart. Cloudflare keeps the old secret valid for a grace period,
  so run the sync within that period. First rollout of the check: deploy the
  release (`next_deploy.py all --execute`; it also regenerates the Caddy
  static routes that carry the `/forgot-password` CSP), then run
  `next_vault.py sync --execute`. Signup stays closed on each node until the
  sync reaches it.
- **Tests and development**: when `FORKMESH_PLATFORM` is not `vps` and no
  secret is set, the App uses Cloudflare's test keys: site key
  `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`.
  Both always pass and are answered locally with no network call. On a VPS
  the test pair is accepted only when `TURNSTILE_TEST_MODE=1` is also set
  (the host e2e test sets it). Never put that setting in the fleet.

### Native app builds (Codemagic)

Codemagic builds the native iOS app (`native/ios`) from this repository,
cloned privately from the core nodes, never from production or GitHub.

  `/var/lib/forkmesh-next/git/forkmesh-next.git` (root:caddy, 0750/0640).
  Caddy serves it with Git's dumb-HTTP protocol under `/git/` on

  imports by glob, so a node without it just has no `/git/` route.
  Clone URL (the password is never printed):
  `python3 tools/next_git_host.py url` →
  `https://fmnext-ci@app.next.forkmesh.com/git/forkmesh-next.git`.
- **The Codemagic app**: `forkmesh-next`, appId `6ab4bf314d17308cbfb476e6`
  (team `6aac6d270e825278dd34c3b4`, the same team as production), recorded

  ```sh
  python3 tools/next_codemagic.py build ios-native-build --execute   # pushes, then starts it
  python3 tools/next_codemagic.py build ios-native-adhoc --execute --wait
  python3 tools/next_codemagic.py status <build-id> --logs   # steps + failed-step logs
  ```

  for another `--branch`, which `push` does not send). Codemagic sees only
  what was pushed.
- **Ad hoc builds go to the `forkmesh` app** (2026-10-01): `build
  ios-native-adhoc --mirror` (what `.forkmesh/shortcuts/deploy-native-ios-ad-hoc.sh`

  `forkmesh-next` has no signing group yet. `--wait` prints each step as it
  starts and ends and up to 20 new lines of the running step's log every 15 s.

  Codemagic clones with `--depth 50` by default ("dumb http transport does
  not support shallow capabilities"). Every workflow sets
  `CM_CLONE_UNSHALLOW: "true"` and `next_codemagic.py build` passes it too;
  keep it in any new workflow, and start builds from the UI or webhooks
  only for these workflows.
- **The password is in Codemagic's build logs**: the "Fetching app sources"
  step prints the clone URL with the password to everyone who can see the
  team's builds. It opens this read-only mirror and nothing else, but treat
  it as known to the Codemagic team. `status --logs` masks it here.
- **First-time setup** (done 2026-09-24): `install nN --steps files,start`
  on each core (the Caddyfile import), then
  `python3 tools/next_git_host.py setup --execute` (repo dirs, a new

### Caddy version

The cores run Caddy from the upstream release, not Debian's 2.6.2, whose
routes reload panicked (`context: internal error: missing cancel error`) on
4 of about 6 deploys on 2026-09-24.

- **Where it comes from**: `[caddy]` in `deploy/fleet.toml` pins the version
  and the sha256 of `caddy_<version>_linux_amd64.tar.gz`. Put that file in
  `~/projects/forkmesh/data/fleet/dl/` after checking it against the release's
  `caddy_<version>_checksums.txt` (sha512). That file's cosign signature
  must verify with the attached certificate, whose SAN is the
  `caddyserver/caddy` release workflow for that tag.
- **Why a pinned binary and not the Cloudsmith apt repository**:
  - It is the same pattern as rqlite: an explicit version bump in
    `fleet.toml`, checked here and on the node.
  - No third-party apt source or signing key is trusted on internet-facing
    nodes, and `unattended-upgrades` can never change Caddy outside an IDS
    window.
  - `/usr/local/bin` is a lockdown path for the IDS, and `/usr/bin` is not
    watched.
  - Debian's package stays installed. It keeps the `caddy` user, `/etc/caddy`
    and `caddy.service`, and its `/usr/bin/caddy` is the untouched fallback.
- **Install / upgrade**: `next_fleet.py install nN --steps caddy --execute`
  (part of `INSTALL_STEPS`, after `files`). It works like this:
  1. It verifies the tarball here and on the node, plus the binary's own
     sha256 and its `version`.
  2. It runs `caddy validate` on `/etc/caddy/Caddyfile` with the **new**
     binary, as root, with a throwaway `HOME`. If validation fails, nothing
     changes.
  3. It installs `/usr/local/bin/caddy` and
     `/etc/systemd/system/caddy.service.d/forkmesh-next-binary.conf`. That
     drop-in only resets `ExecStart` and `ExecReload` to the new binary;
     `forkmesh-next.conf` keeps the sandbox, `Restart=on-failure` and the
     certsync `ExecStartPre`.
  4. It restarts Caddy and checks that it serves `nN.<domain>/readyz` and
     that its main PID runs `/usr/local/bin/caddy`.
- **IDS**: the step first pushes a signed expectation with the exact sha256
  of both files and `allow processes,listeners`. `ids.json` accepts either
  binary for the `caddy` user.
- **Restore**: if anything fails after the install, the step itself runs
  `caddy-debian`. That removes the drop-in, restarts Debian's caddy, checks
  it serves, then removes `/usr/local/bin/caddy`, under its own expectation
  (both files expected gone). By hand:
  `install nN --steps caddy-debian --execute`.
- **Rollout**: one node at a time, n3, n2, then n1. On each node, run
  `--steps caddy`, then `--steps files,start`, which renders the new
  `ids.json` and restarts the IDS inside the step's window. Then:
  - check `/readyz` and `next_ids.py status nN`;
  - run `systemctl reload caddy` twice and check `journalctl -u caddy` for
    `panic`.
- **Compatibility (checked 2026-09-24 against 2.11.4)**: these all validate
  with 2.11.4, in `files`, `acme` and `internal` modes: the rendered
  Caddyfiles of n1–n3, the deployed release routes, the certsync includes
  and the private Git snippet. The adapted JSON matches 2.6.2's except for
  matcher names and import-chain order. `deploy/tests/test_caddy.py` passes
  with 2.11.4 on `PATH`, including precompressed serving, `_headers` and
  basic auth. The one warning was `basicauth` (deprecated for `basic_auth`) in
  `git-private.caddy`; every core runs 2.11, so `tools/next_git_host.py`
  now writes `basic_auth`. Debian's 2.6.2 fallback does not know it, so
  falling back to `/usr/bin/caddy` needs the snippet rewritten first.
- **Status 2026-09-24**: n3, n2 and n1 run 2.11.4 from `/usr/local/bin`.
  Each was drained from DNS first, reloaded twice without a panic, and left
  with the IDS normal. The deploy of d8421cec150b then activated all three in
  a single pass. Debian's 2.6.2 remains at `/usr/bin/caddy` as the fallback.
- **Drain**: never pipe `next_dns.py drain` into `head`. SIGPIPE stops it
  after the first record, with the state not saved; `ensure --execute`
  repairs that.
- **Version choice**: 2.11.4 (2026-06-03), the current stable release.
  2.10.2 is the last 2.10 release. It lacks the 2.11 security fixes
  (CVE-2026-27585 to 27590: path and host matcher bypasses, among others).

## 5. Recovery

- **Every node restarted at once** (power loss, a fleet-wide reboot): the
  site answers 503 `{"error":"sealed"}` until the desktop unseals one node.
  With the timer installed this happens within a minute of the desktop
  being on; by hand: `python3 tools/next_vault.py unseal --execute`. The
  peers unseal each other from then on.
- **A node will not unseal**: `journalctl -u forkmesh-app | grep vault:`
  on the node. `wrong_key` / `vault_tampered` mean the rows do not match
  this key (compare `next_vault.py status` key ids); `vault_empty` means
  `sync` never ran; `db_unavailable` means rqlite has no leader yet (the
  helper retries for 30 s); `rate_limited` means wait a minute.
- **Lost DATA_KEY**: the vault rows and every row the app encrypted with
  `DATA_KEY` are unrecoverable. Keep an offline copy of `config/DATA_KEY`.
- **Turning the vault on for a running fleet** (one node at a time, after a
  release that includes it): `next_deploy.py all --execute` (migration
  0194), `next_vault.py sync --execute`, then per node
  `next_fleet.py install nN --steps files,secrets,start --execute` (the unit
  goes sealed; `secrets` pushes only the bootstrap credentials and deletes
  the other `.cred` files by name, refusing unless the unit is already in
  vault mode) and `next_vault.py unseal nN --execute` (or wait for its peers).

## 6. Destroy

```sh
python3 tools/next_fleet.py destroy r1 --yes              # plan
python3 tools/next_fleet.py destroy r1 --yes --execute    # a runner holds no state
```

Destroying a core node is refused while fewer than 3 healthy rqlite voters
would remain; use `replace-core` instead. Tearing down the whole cluster
destroys the database. To do it anyway:

1. Take a backup: `tools/next_backup.py run --execute`.
2. Set `[dns] reconciler = "off"` and re-render the nodes (or just seal
   them), so no node changes DNS while they disappear.
3. Destroy each core node with `destroy nN --yes --execute --force`.

`--force` skips only the quorum check. The `fmnext-` label and
`forkmesh-next` tag checks cannot be bypassed. Remove the DNS records in the
Cloudflare dashboard (the tool never empties a record set).

## 8. Known gaps

- **Edge identity**: closed. The host verifies `x-forkmesh-edge-client`
  before the App sees the request (`app/host/forkmesh_host/request_guard.py`,
  contract in `deploy/core/edge_client.md`) and only then replaces
  `cf-connecting-ip` / `cf-ipcountry`; the header itself never reaches the
  App code.
- **Runner provisioning**: `install r1` sets up the base system, firewall
  and daemon (`role: runner`, one job at a time; the daemon runs as root and
  starts each job as the unprivileged `forkmesh-job`, section 9). It does
  not install the `claude`/`codex` CLIs or sign them in; do that through the
  relayed login (docs/RUNNERS.md). The merged core
  and runner daemon configs pass the daemon's own `--check` (checked offline
  against a local build); with an older daemon that lacks `role` the
  installer drops the field and warns.
- **Country lookup**: Caddy sets no country header (the DB-IP Lite lookup is
  not built), so directly reached `app.next` requests have no country.
- **Python version**: nodes use Debian's Python 3.13, not 3.14 via `uv`.
  Release venvs are built offline from a cp313 wheelhouse.
- **Release pruning**: old releases stay in
  `/opt/forkmesh-next/app/releases/`, so delete them by name when disk runs
  low.
- **rqlite `-fk`**: turned on (`rqlite.fk = true`) to match D1. All migrations,
  `PRAGMA foreign_key_check`, and the signup/login/session flows pass with it.
- **Restore drill**: the nightly restore into a throwaway instance is not
  automated. The backup is verified locally with `integrity_check` only.

## 9. Security hardening (audit 2026-09-24)

What the node files now enforce (`deploy/core/render.py`, `tools/next_fleet.py`):

- **Caddy**: the admin API is the unix socket `/run/caddy/admin.sock` in
  caddy's 0700 `RuntimeDirectory` (no TCP `localhost:2019`); `caddy reload`
  (the unit's ExecReload, certsync's reload) finds it in the Caddyfile.
  Server timeouts `read_header 10s`, `read_body 5m` (it is per listener and
  must fit a Git push on `nN.next`; WebSockets are not affected),
  `idle 2m`, `max_header_size 64KB`. Request bodies: 16 MB on app/world,
  32 MB for `POST /api/repo/<owner>/<repo>/pulls` (the App host enforces the
  same limits), 1 GB for Git pushes on the per-node name. Caddy 2.6 answers
  an over-limit proxied body with 502 rather than 413; the body still stops
  at the limit. HSTS and `nosniff` are set (deferred) on every response,
  proxied, redirected or generated. The drop-in sandboxes Caddy
  (`ProtectSystem=strict`, only `CAP_NET_BIND_SERVICE`,
  `SystemCallFilter=@system-service`, `MemorySwapMax=0`, no metadata
  service).
- **App host request errors** (`app/host/forkmesh_host/asgi.py`,
  `app/src/app_runtime.py`): a client that disconnects while its body is
  being read gets 499 and is neither counted as a host error nor written to
  `error_log`, so it no longer shows on /status as a 500 (it was seen on
  `/api/runners/claim`). A query or form with more fields than a parser's
  `max_num_fields` ("Max number of fields exceeded") answers 400, on the
  repository fast path and in the Worker.
- **certsync**: pulled pairs must chain to a system CA for TLS server use,
  cover the name, be valid now and expire within 100 days; Caddy's `local`
  issuer is never collected. The pair server authenticates with its own
  `FORKMESH_CERTSYNC_SECRET` (only `fmnext-certsync.service` and
  `fmnext-cert-sync.service` load it), so the app, which holds the mesh
  secret, can no longer download the TLS private keys. The `files` step
  disables and removes the old `fmnext-cert-{export,pull}.{service,timer}`
  and `cert-{export,pull}.{service,timer}` units by exact name on every core.
- **nftables output rules on the cores** (by socket uid): Raft 4002 only
  from `rqlite`; rqlite HTTP 4001 only from `root` and `forkmesh-app`; mesh
  8792 only from `forkmesh-app`; certsync 8793 only from `root` (the
  `fmnext-cert-sync` round); 169.254.0.0/16 only from `root` (cloud-init).
  Units also set `IPAddressDeny=169.254.0.0/16`.
- **Swap and ptrace**: `MemorySwapMax=0` on rqlite, Caddy and both certsync
  units (the app already had it); `kernel.yama.ptrace_scope = 1`.
- **sshd** (`base` step, checked with `sshd -t` first): no agent or X11
  forwarding, `AllowTcpForwarding local` (not `no`: `next_backup.py` and
  `next_deploy.py migrate` reach rqlite through `ssh -L`), `PermitTunnel no`;
  `50-cloud-init.conf` (`PasswordAuthentication yes`) is deleted.
- **Vendor leftovers** (`base`): root's password is locked (`passwd -l root`
  where sshd uses PAM, else `usermod -p '*'`; key logins keep working),
  `cloud-init-log-reader.service` (a root `less` on tty4) is masked, and
  `linuxuser` is locked and removed (never while it has processes).
  **The Vultr web console can then no longer log in as root**: to get a
  console shell, boot the instance into Vultr's rescue ISO/recovery mode
  and mount the disk.
- **The daemon** has no `systemd-journal` group (it never reads the
  journal) and `UMask=0077`; the installer makes `/etc/forkmesh` and
  `/var/lib/forkmesh` owner-only.
- **The runner** (`r1`): the daemon runs as root with only
  `CAP_CHOWN CAP_DAC_OVERRIDE CAP_FOWNER CAP_KILL CAP_SETUID CAP_SETGID`
  (`systemd-run --scope --uid/--gid` changes the job's user and group inside
  the daemon's own process, so it needs the last two) and starts every job as
  the system user `forkmesh-job` (home `/var/lib/forkmesh-job`, 0700, no
  shell, no groups) through the system manager (`runner.jobUid`, set on the
  node from `id -u forkmesh-job`). Job workdirs live in
  `/var/lib/forkmesh-runner/work` (0711 root), outside the daemon's 0700
  state. The job user cannot read the node key, `mirror-node.json` or its
  `connectorToken`. nftables refuses the job user every metadata, RFC 1918,
  CGNAT, loopback (except DNS to a 127.0.0.53 stub), WireGuard, and IPv6
  loopback/ULA/link-local address, and refuses `forkmesh-node` the metadata
  service. `mirrorUrl` is dropped from the runner's config (a runner serves
  nothing, so no `r1.next` DNS record is needed).

### Rollout (one node at a time; dry-run first without `--execute`)

**Order matters.** The new App answers 421 to any Host outside
`FORKMESH_PUBLIC_HOSTS` (it falls back to only app/world without it), so
the node files that render that variable must be on every core **before**
the App release; otherwise `https://nN.next.forkmesh.com/readyz` (the DNS
health probe) fails. The full sequence:

1. Operator box: `python3 tools/next_backup.py keygen --execute` (done
   2026-09-24), then move `config/backup-age.key` offline; nightly backups
   refuse to run without `config/backup-age.pub`.
2. `init-secrets` and the per-core `base,secrets,files,start` + `daemon`
   loop below (old App keeps running; it ignores the new variables).
3. App release: `python3 tools/next_deploy.py all --execute` (Host
   allowlist, body caps, egress guard, edge-client check, static mesh map,
   admin table denylist, AP outbound off). Then check
   `curl -fsS https://nN.next.forkmesh.com/readyz` for every node and
   `curl -sI https://app.next.forkmesh.com/api/version` (HSTS, nosniff).
4. Runner: build the daemon with this release, `install r1 --steps
   base,files,start,daemon`, move the Claude login (below), then set r1's
   `allowed_owners` (docs/RUNNERS.md; until then the pool serves nobody),
   and look for `runner: jobs run ... uid=<n> ip-filter=true` in
   `journalctl -u forkmesh-mirror-node`.
5. Optional: imported webhooks/AP targets on production hosts now fail by
   design; `FORKMESH_EGRESS_ALLOW=host:port` is the only exception list.

```sh
# 0. The new certsync secret (only the missing value is generated).
python3 tools/next_fleet.py init-secrets --execute
# 1. Each core in turn. `secrets` must precede `files`: the new certsync
#    units load FORKMESH_CERTSYNC_SECRET.cred. `start` restarts Caddy (its
#    admin moves from TCP to the unix socket, so the reload falls back to a
#    restart: a second of downtime on that node).
for n in n1 n2 n3; do
  python3 tools/next_fleet.py install $n --steps base,secrets,files,start --execute
  python3 tools/next_fleet.py install $n --steps daemon --execute   # UMask, modes, no journal group
  # check before the next node: curl -fsS https://$n.next.forkmesh.com/readyz
  #   and journalctl -u fmnext-cert-sync -n 5 on the node
done
# 2. The runner: base (job user, dirs, sshd), files (unit, nftables), start,
#    then the daemon (root, jobUid).
python3 tools/next_fleet.py install r1 --steps base,files,start,daemon --execute
```

While the cores run mixed secrets, certsync peers on the old secret look
dead to the new ones; the installed certificates keep being served (they
expire 2026-12-23, far from the 30-day renewal window), and the rounds agree
again once the last core is done.

Risks to watch: `sshd -t` guards the SSH drop-in, and a failing one is
removed, so key login is never lost; keep one SSH session open on the node
while its `base` step runs anyway. The nftables output rules are checked
with `nft -c` in the `files` step and loaded atomically in `start`; if
rqlite or the app misbehave afterwards, `journalctl -k` shows nothing (the
rules count and reject), so compare `nft list ruleset` counters.

**Move the runner's Claude login to the job user** (the website sign-in now
writes into `forkmesh-job`'s home; the old login is readable by the
daemon's user only and must not stay there):

```sh
# on r1, as root, after the daemon step
install -o forkmesh-job -g forkmesh-job -m 0600 \
  /var/lib/forkmesh/.claude/.credentials.json /var/lib/forkmesh-job/.claude/.credentials.json
rm -f /var/lib/forkmesh/.claude/.credentials.json
# same for codex if used: /var/lib/forkmesh/.codex/auth.json -> /var/lib/forkmesh-job/.codex/
# The CLIs must be executable by forkmesh-job: install them system-wide
# (e.g. under /usr/local), not in /var/lib/forkmesh (now 0700).
systemctl restart forkmesh-mirror-node
```

Or skip the copy and sign in again from `/dashboard/runners`.

### Recommendations for the user (not automated)

- **CAA (recommendation only, do not add from here)**: CAA records apply to
  the whole `forkmesh.com` zone, including production, so a wrong set would
  stop production's certificates from renewing. If production's owner
  agrees, the set would be `forkmesh.com. CAA 0 issue "letsencrypt.org"`,
  one `issue` line per CA production and Cloudflare use (Cloudflare's
  Universal SSL needs `pki.goog`, `digicert.com`, `ssl.com` and
  `letsencrypt.org`), `0 issuewild` likewise, and
  `0 iodef "mailto:<security contact>"`. Check every issuer in use first
  (crt.sh for `forkmesh.com`).
- **Operator box**: encrypt the disk (LUKS, or at least an encrypted home
