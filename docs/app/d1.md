# Database (`DB`)

Part of [the App docs](README.md). The App's database of record has the
binding `DB`. On the core nodes it is rqlite (Raft) behind a D1-compatible
adapter (`app/host/forkmesh_host/d1_rqlite.py`), so the code keeps D1's SQL
dialect and API shape. Room objects keep transient state in it too
([cron-and-durable-objects.md](cron-and-durable-objects.md)); Git bytes are
never in the database. How the cores replicate it and what happens when
cores fail: [architecture](../architecture.md).

## Storage model

Each table stores HMAC blind-index columns for lookups and uniqueness plus one
AES-GCM encrypted JSON `data` blob (`blind_index` and the `seal` methods of
the runtime adapters). The App holds `DATA_KEY`, so this protects data at rest
but is not zero-knowledge ([encryption](../encryption.md)). Some
tables are deliberately plaintext (rate windows, operational counters).

## Schema and migrations

- `app/migrations/NNNN_*.sql` are applied once each, roll-forward
  (`tools/rqlite_migrate.py` on the cores); `app/migrations/down/` holds the
  reverse scripts. Numbers are unique and increasing; on a collision `main`
  keeps its number and the branch renumbers.
- `app/src/schema.py` holds runtime DDL. `ensure_schema` checks a fingerprint
  in `schema_meta`, so a cold process normally does one SELECT; any change to
  `schema.py` triggers one single-flighted replay.
- World and package tables are created by their own modules' DDL, plus World
  migrations in `app/migrations`.

## Read budget

- `app/src/d1_read_guard.py`: `shared_read` caches one JSON copy of a heavy
  read. Its switch (the `d1_read_guard` row) is `auto`, `on` or `off`;
  conserving stretches TTLs and makes orientation-only readers serve a
  fallback.
- On a core the Cache API is per process (`app/host/forkmesh_host/js.py`, an
  8 MB LRU), so `shared_read` trusts its in-process copy for the reader's
  whole TTL; the 15-second recheck of a shared cache copy in the code only
  matters where several processes share one cache.
- Public snapshots (`app/src/public_snapshots.py`, `public_api_snapshots`):
  anonymous hot GETs are served from validated rows republished by cron and
  by the change doorbell.
- Clients read on change, not on a timer
  ([polling elimination](../operations/polling-elimination.md)).
- The World infrastructure table inventory
  (`world/src/world_infrastructure.py`) counts 50 tables per `UNION ALL`
  statement and falls back to one table at a time only when a batch fails
  (one `COUNT(*)` per table would be 257 statements a rebuild).

## Write-watched memos

`_d1_write_watch` in `app/src/entry.py` sees every statement this process
sends. A write to a watched table bumps `_D1_WATCH_GENERATIONS`, and a memo
keyed on that generation is dropped by the next reader in the same process.
Writes from other cores reach a memo only when its TTL lapses, so each TTL is
also how long another core can serve the old answer.

- `mirror_https_endpoints`: `_d1_snapshot` holds the routing columns
  `_https_mirror_candidates` reads for 30 seconds, the same ceiling as the
  public catalog memo, so clone advertisements, upload-packs and routed browse
  reads do not scan the table. A transport failure or rejected request marks
  the endpoint unhealthy with a local write, which drops the snapshot at once.
- `_repo_is_private`: a public verdict is reused for up to 30 seconds while
  `catalog_rev` (probed at most every 10 seconds) and this process's
  `repositories` generation are unchanged. Every catalog mutation bumps
  `catalog_rev`, and `_https_mirror_public_context_cache_clear` and
  `_forget_repo_closed` drop it. The decrypted catalog and routing context
  already serve on the same ceiling, so this adds no exposure, and public
  `info/refs` and `git-upload-pack` skip the `repositories` read. A closed
  verdict keeps its 5-second memo.
- `_claimed_node_signing_pubkeys`: the keys a claimed node may sign with are
  held for 10 seconds per node (runner polls, core pool status, replica
  reports and SSH Git auth would otherwise read up to four rows per signed
  request). A write to `users`, `account_devices` or `nodes` (other than the
  `last_seen` heartbeat stamp) drops them. A revoked device key stops working
  on another core within 10 seconds.

`clone_sticky` pins a clone's upload-pack to the endpoint that served its
`info/refs`. A `307` to a proven direct mirror writes no pin: Git moves the
remote onto the redirect target, so that clone's upload-pack goes to the
mirror and never asks the relay for the pin.

## Operating it

- The desktop Database tab lists tables and edits rows through the admin
  database route (`app/src/admin_database.py`).
- `repositories` is readable in the admin Database tab and the web console but
  delete-only: inventory reports `deletable: true, writable: false`, and an
  insert or update is refused. Deleting a row runs
  `admin_purge_repository_rows`, the same purge as the admin repository delete
  in `catalog_routes.py`: a tombstone so the owner's node cannot republish,
  `_delete_repo_scoped_state`, then the named state, bounties, chat rooms and
  project funds (only when the sealed record decrypts and its owner/name hash
  back to the row's `key_bi`), and one `repository.delete` audit row per
  repository. A desktop request deletes at most 50 repositories.
- The phone's Admin > Database page uses `GET /api/admin/phone/database`: a
  bearer session whose account passes `_is_admin` (never a cookie), only
  `op=inventory` and `op=rows`, at most 50 rows per page, read-only.
- Statement logging on a core: each statement line names its caller,
  `D1 <kind>: <sql> [N args] (for <caller>) (from <file> in <function>)`.
  `app/host/forkmesh_host/d1_caller.py` keeps the caller per invocation
  (`<METHOD> <path>, IP <client>`, `cron`, `queue <name>`,
  `alarm <class>`), plus `user <name>, session <first 8 characters>` once a
  session is accepted. Token secrets are never written. Cross-core calls carry
  the clause in the `x-fm-d1-caller` header, which is stripped from client
  requests.
- With `FORKMESH_HOST_D1_LOG=1`, each single statement is followed by
  `D1-done <ms> ms, <rows> rows, <changed> changed[, local|http][, failed] #<key>`,
  where `<key>` is the first 10 hex digits of the SHA-1 of the logged
  statement text; the desktop joins the two lines by that key.

## Retired tables (audit #682)

The Database tab's audit findings (`ADMIN_DATABASE_AUDIT_FINDINGS` in
`app/src/admin_database.py`) retired these:

- `system_status_minute`, `system_status_hourly` and `system_status_daily`:
  superseded by their `*_batch` tables; status history comes only from the
  batch tables.
- `host_presence`: no writer since repository sockets retired; the live node
  count comes from signed endpoints and account heartbeats.
- Migration 0294 drops `commit_inbox` and `forkmesh_d1_migrations` (an old
  migration tracker) and creates the twelve tables `schema.py` alone used to
  create, so a database replayed from migrations has them.
- By the two-deploy rule (drop a table one deploy after the code stops
  using it), the four retired tables above are dropped by a later migration, one deploy
  after 0294. `telemetry` waits for an export and the owner's yes; the custody
  tables wait for the custody record's sign-off.
- `app/tests/test_d1_audit_repairs.py` keeps SQL off the retired tables and
  checks the catch-up DDL against `schema.py`.
- `tools/next_rekey.py` does not list `commit_inbox` or `host_presence`.
  Until the follow-up drop lands, a `--strict-registry` rekey of production
  refuses the empty `host_presence.repo_bi`; a normal rekey re-keys it as an
  unregistered column.

## Traps

- `DATA_KEY` has no key-version byte, so it cannot be rotated without
  re-encrypting every row ([rekey](../operations/rekey.md)).
- The migration set alone does not rebuild a complete database: the legacy
  custody tables `bounty_wallet` and `issue_bounty` exist only through
  runtime DDL.
- rqlite freezes `RANDOM()` and `'now'` in triggers and views.
- rqlite answers `store not open` while a node is still opening its store (a
  restart or a snapshot restore). `d1_rqlite.py` maps it, like the raft
  leader and timeout errors, to the "overloaded" D1 error, so the router
  answers 503 + Retry-After instead of opening a 500 error group. A query a
  follower forwards to a leader that has just died fails with
  `connection reset by peer` or `connection refused`; those (and
  `broken pipe`, `i/o timeout`) map to "overloaded" too.
- Migration 0268 drops `idx_org_bot_token_usage_token_time` (and `schema.py`
  does not create it): no query reads `org_bot_token_usage` by `token_id`;
  the reads are by `org_bi` and the retention DELETE by `used_at`, each with
  its own index.
