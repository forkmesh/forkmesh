# D1 database

The App's database of record is the D1 database `forkmesh` (binding `DB`).
Durable Object storage is for transient room state only; Git bytes are never
in D1.

## Storage model

Each table stores HMAC blind-index columns for lookups and uniqueness plus
one AES-GCM encrypted JSON `data` blob (`app/src/entry.py`, "D1 storage"
section; `blind_index`, the `seal` methods of the runtime adapters). The
Worker holds `DATA_KEY`, so this protects data at rest but is not
zero-knowledge. Some tables are deliberately plaintext (rate windows,
operational counters); the per-table inventory is in
`docs/operations/database-audit-2026-09-10.md`, section 2.

## Schema and migrations

- `app/migrations/NNNN_*.sql` are applied once each by `app/migrate.sh`
  (`wrangler d1 migrations apply`) before every deploy. `app/migrations/down/`
  holds the reverse scripts. Numbers are unique and increase; when two
  branches take the same number, `main` keeps its number and the branch
  renumbers.
- `app/src/schema.py` holds runtime DDL. `ensure_schema` checks a fingerprint
  in `schema_meta` so a cold isolate normally does one SELECT; any change to
  `schema.py` changes the fingerprint and triggers one single-flighted replay.
- World and package tables are created by their own modules' DDL
  (`world/src`, `marketplace/packages/*/content/worker`), plus World
  migrations kept in `app/migrations`.
- Recent migrations: 0184 plan trials, 0186 read guard, 0187 ad network,
  0188 repository webhooks, 0189 drop Polar tables, 0190 drop
  `api_metrics_minute`, 0191 organization agent attachments, 0213
  ecosystem projects ([ecosystem.md](ecosystem.md)), 0217 code challenges
  ([challenges.md](challenges.md)), 0251 workflows

## Read budget

Workers Free bills rows read (5 million a day, account-wide). Tools to stay
inside it:

- `app/src/d1_read_guard.py`: `shared_read` keeps one JSON copy of a heavy
  read per colo in the Cache API. Its switch (the `d1_read_guard` row, set from
  the desktop Database tab) is `auto`, `on` or `off`; conserving stretches TTLs
  and makes orientation-only readers serve their fallback.
- Public snapshots (`app/src/public_snapshots.py`, `public_api_snapshots`
  table): anonymous hot GETs are served from validated rows republished by
  cron and by the change doorbell, not by a live scan.
- Read on change, not on a timer: clients learn about changes from socket
  frames (`www/docs/operations/polling-elimination.md`).

## Operating it

- The desktop Database tab lists tables and edits rows through the admin
  database route (`app/src/admin_database.py`).
- The phone's Admin > Database page reads the same inventory and row pages
  through `GET /api/admin/phone/database` (2026-10-01). The phone has no
  Ed25519 admin key, so this route takes an `Authorization: Bearer` session
  whose account passes `_is_admin` (the same check the bearer user actions
  use; a browser cookie never qualifies). It serves only `op=inventory` and
  `op=rows`, caps a page at 50 rows, and has no write path. Before it
  existed the page called a route nothing served and showed "This server
  does not offer that yet."
- Every D1 statement is logged with the Worker file that issued it and who
  requested it, so queries appear in the desktop's cloud log (`fb826b2c0`,
  `4ba9c44c9`).
- On a core host (2026-09-28), each statement line also names its caller:
  `D1 <kind>: <sql> [N args] (for <caller>) (from <file> in <function>)`.
  `app/host/forkmesh_host/d1_caller.py` keeps one caller per invocation in a
  context variable: `<METHOD> <path>, IP <client>` for a request (a WebSocket
  keeps its upgrade request for the socket's life), `cron`,
  `queue <name>` or `alarm <Durable Object class>`. Once
  `_account_session_lookup` accepts a session, the rest of that invocation
  adds `user <name>, session <first 8 characters of session_id>`; match the
  prefix against `account_sessions.session_id` to find the session row, its
  device and its client IP. The token secret and digest are never written. A
  Durable Object call to another core carries the clause in the
  `x-fm-d1-caller` mesh header, which `forward_headers` strips from client
  requests so it cannot be forged. On Cloudflare `_D1_QUERY_CALLER` stays
  unset and the lines are unchanged; the tail event already names the
  requester there.
- On a core host (2026-10-01), each single statement is followed by a timing
  line once it finishes: `D1-done <ms> ms, <rows> rows, <changed> changed[,
  local|http][, failed] #<key>`. `d1_caller.note_done`, called from
  `D1PreparedStatement._execute` in `d1_rqlite.py`, writes it only while
  `FORKMESH_HOST_D1_LOG=1` (`runtime.py` turns it on with the statement lines).
  `<key>` is the first 10 hex digits of the SHA-1 of the statement text as the
  statement line prints it: whitespace collapsed, cut at
  `D1_QUERY_LOG_MAX_CHARS` with `...`, no `[N args]` suffix. The desktop
  computes the same key to join the two lines, so the line carries no SQL and
  no bound values. `local` means the read was answered by the node's own
  replica; `http` means rqlite's HTTP API. Batches and `exec` write no timing
  line. The prefix `D1-done` does not match the `D1 <kind>:` statement pattern,
  so an older desktop does not count the timing lines as statements. The node
  log reader redacts credential words (`token = ?`) in statement lines, so
  the desktop's key for such a statement differs and its timing is only
  counted as unmatched.
- Cleanup work items, with ready prompts: `www/docs/operations/d1-database-cleanup-plan.md`.
- Export: `wrangler d1 export forkmesh --remote --output <file>` through
  `app/pywrangler.sh`; see the plan's step S0.1.

## Traps

- `DATA_KEY` has no key-version byte in the ciphertext yet, so it cannot be
  rotated without re-encrypting every row (cleanup plan S4.1, S4.2).
- The migration set does not rebuild a complete database from scratch:
  some tables exist only through runtime DDL (audit section 3.4; cleanup
  plan S0.2).
- `app/migrate.sh` refuses migrations that delete `ap_followers`.
